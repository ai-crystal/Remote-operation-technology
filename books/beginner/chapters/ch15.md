# 把文件送到远方

> 传大文件之前，先想清楚断了怎么办。

## 15.1 传到百分之九十

你在本地有个三个 G 的数据集，要传到服务器上。网上搜了一下，`scp` 最简单，复制一条命令就能用：

```bash
scp dataset.tar.gz alice@203.0.113.24:/home/alice/
```

传了四十分钟，进度到百分之九十，网络抖了一下，连接断了。终端回到提示符，服务器上留了一个不完整的文件，而 `scp` 不会告诉你它是残缺的——文件名、大小看起来都对，只有解开的时候才发现少了最后一段。你只能从头再传一遍，又四十分钟，心里一直悬着。

这件事有一个更稳的做法，但在讲它之前，先算一笔账：三个 G 的数据，在家用宽带上行 10 Mbps 的情况下，理论上要传四十分钟左右（3 GB ≈ 24000 Mb，除以 10 Mbps 就是 2400 秒）。也就是说，这四十分钟里只要有一次抖动，前面的时间就全白费。文件越大、链路越差，从头再来的代价越高。所以真正要解决的不是“怎么传得更快”，而是“断了以后怎么不用从头开始”。

## 15.2 scp 是什么

`scp` 和后面的 `rsync` 都在你自己的电脑上敲。这一点先分清：起点是你的电脑，终点是服务器，命令里的路径分别属于两台机器。左边是本地路径，右边是 `用户@主机:路径` 的形式。

`scp` 是 secure copy 的缩写，走的就是 SSH 那条加密通道，所以认证方式、端口、密钥都和第 8 章讲的一模一样。用法和 `cp` 很像：

```bash
scp 本地文件 alice@主机:/远端路径       # 上传
scp alice@主机:/远端文件 ./             # 下载
scp -r ./mydir alice@主机:/home/alice/  # 整个目录
scp -P 2222 file alice@主机:/tmp/       # 指定端口，注意是大写 P
```

最后一条值得单独记一下：`scp` 的端口参数是**大写 `-P`**，而 `ssh` 是小写 `-p`。这是历史遗留的不一致，输错了不会报“参数不对”，而是把它当成一次普通的传输，连到默认的 22 端口，然后超时，很容易误判成网络问题。

`scp` 的优点是简单，几乎所有机器上都有，不需要额外安装。缺点是它把“传文件”这件事做得很朴素：从开头传到结尾，中间不记录进度，断了就从零开始。OpenSSH 9 之后，`scp` 底层其实已经改用 SFTP 协议传输了，行为和以前略有差别，但“没有断点续传”这一点没变。所以传几十兆的小文件完全够用，传几百兆以上就该换工具。

## 15.3 rsync 为什么更好

```bash
rsync -avz --progress --partial dataset/ alice@203.0.113.24:/home/alice/dataset/
```

这条命令里的几个参数，各自解决一个问题。`-a` 是归档模式，等于一次性打开“保留权限、保留时间戳、递归目录、保留符号链接”这一组选项。它保证传过去的文件不只是内容一样，属性也一样。少了它，传完会发现文件时间全变成“刚刚”，依赖时间的构建工具会以为所有文件都改过。

`-v` 显示过程，`--progress` 显示每个文件的进度和速度。`-z` 在传输时压缩，对文本、日志、代码效果明显，对已经压过的图片和视频基本没收益，反而多耗一点 CPU。

`--partial` 是断点续传的关键：传了一半断掉，它把已收到的部分留在临时文件里，下次重跑同一条命令时接着传。

rsync 真正厉害的地方在于它**只传变化的部分**。它先比较两边的文件列表，大小和修改时间都一样的直接跳过；确实不同的，再用“滚动校验和”比较内容，只把真正改变的块传过去。所以第二次同步一个几乎没变的项目目录，通常几秒钟就结束，而不是再传一遍几百兆。它还有几件 scp 做不到的事：

- **排除规则**：`--exclude "*.log"` 跳过日志，`--exclude ".git"` 跳过版本库，`--exclude-from` 从文件读一长串规则。传项目目录时特别有用。
- **删除多余文件**：`--delete` 让远端严格等于本地，多出来的删掉。这个参数很危险，先加 `--dry-run` 看一遍它会删什么，确认无误再去掉。
- **限速**：`--bwlimit=2M` 把带宽限制在每秒 2 MB。在共享链路上传大文件，不限速会把别人的视频会议卡掉。
- **走非默认端口**：`-e "ssh -p 2222"` 指定用哪条 SSH 命令连接。

有一个细节必须注意：**源路径末尾有没有斜杠，含义不同**。`dataset/` 表示“把目录里的内容传过去”，`dataset` 表示“把这个目录本身传过去”。少写一个斜杠，远端就会多出一层 `dataset/dataset/`。这个坑几乎每个人都踩过一次，传完发现路径不对，就是它。

## 15.4 传大文件的三件事

第一件是**先打包**。几千个小文件直接传很慢，因为每个文件都要经历一次打开、协商、关闭，开销比数据本身还大。先 `tar -czf dataset.tar.gz dataset/` 打成一个包，再传这一个文件，效率往往差好几倍。反过来，如果只需要更新其中几个文件，就别打包，让 rsync 去做增量。

第二件是**传完校验**。理论上 TCP 保证了不丢不重，实际上偶发的截断、磁盘写满、中途被杀进程都会留下一个“看起来完整”的文件。最省事的办法是两边各算一次哈希：

```bash
sha256sum dataset.tar.gz          # 本地
sha256sum /home/alice/dataset.tar.gz   # 服务器上
```

两个值完全一致才算成功。这一步只要几秒钟，却能避免后面花两小时排查“为什么解压失败”。第三件是**想清楚断了怎么办**。小文件重传无所谓，几个 G 的文件要有续传方案：用 `rsync --partial`，或者干脆把文件切成几百兆的分片，每片单独传、单独校验，断了只重传出错的那一片。云存储的分片上传是同一个思路：把大对象切成片，每片单独传、单独校验，断了一片重传一片。

## 15.5 不想用命令的话

图形工具也能完成这件事。WinSCP、FileZilla、Cyberduck 都支持 SFTP，底层走的还是 SSH，只是把两端画成两个文件列表，可以拖拽。它们的优势是直观，适合偶尔传几个文件、或者需要边看目录边挑东西的场景。

缺点是出错时信息很少，往往只给一个红叉，既不告诉你卡在哪一步，也不告诉你服务器那边发生了什么。传重要的东西，命令行更可靠：`rsync --progress` 至少能看到传到哪、速度多少、哪个文件失败。

VS Code 的远程文件浏览也能拖文件，它和编辑器结合得紧，改配置文件很顺手，但传几百兆的数据集不合适——它是为“编辑”设计的，不是为“搬运”设计的。

## 15.6 一个安全提醒

用 `scp` 或 `rsync` 的时候，你的私钥在本地，数据在加密通道里，这段路是安全的。但有两件事不要做。

一是**不要把私钥本身传上去**。有些人为了让服务器能连另一台机器，直接把自己的私钥 `scp` 到服务器上，这等于把家门钥匙复制一把放在别人家里。正确做法是在服务器上单独生成一对新密钥，公钥给目标机器，私钥只留在服务器上。

二是**不要往 `/tmp` 里放敏感文件然后忘了删**。`/tmp` 通常是所有用户可读的，而且清理策略因系统而异，可能留很久。传完就删，或者放到自己有权限控制的目录里。

> **这一章记住一句**
>
> 小文件 `scp`，大文件 `rsync`，传完一定校验。
