# 报错翻译器

> 报错不是判决书，是路标。

这一章是一张表，不用背。遇到的时候过来查，或者直接拿原文去搜。每一行都按同一个结构写：英文原文、它到底在说什么、第一步该查什么。表后面几段讲怎么用这张表。

## 22.1 先看清是谁在说话

一条报错里最重要的信息，往往不是它说了什么，而是**它是谁说的**。同一句 `Connection refused`，从浏览器、从 `curl`、从 nginx 日志、从应用日志里看到，指向的位置完全不同。

判断方法很简单：看这条报错出现在哪里。

- 出现在你的终端里，说明是本地客户端在说话，它通常只知道自己这一端发生了什么。
- 出现在浏览器的错误页上，说明是浏览器或中间代理在说话，内容往往被简化过。
- 出现在 nginx 的 `error.log` 里，说明是反向代理在说话，它看到的是“我连不上后端”。
- 出现在应用的日志里，说明是你的程序在说话，它看到的是“我调用的东西失败了”。
- 出现在 `journalctl` 里，说明是 systemd 在说话，它看到的是“进程退出码不是 0”。

一条请求可能经过四五层，每一层都会留下自己的说法。**从上往下读日志**，找到第一层开始报错的地方，那里才是问题的位置。第 13 章那张“十站图”就是用来做这件事的。

还有两个细节值得看。一是**退出码**：`systemctl status` 里那一行 `status=203/EXEC`、`status=1/FAILURE`，比一句“启动失败”精确得多。二是**时间戳**：把应用日志、nginx 日志、系统日志按时间对齐，能看出是谁先出问题。

## 22.2 连接类

这一类最容易被误判，因为“连不上”的现象几乎一样，原因却分布在不同层。

| 原文 | 人话 | 第一步查什么 |
| --- | --- | --- |
| `Connection refused` | 到了机器，但那个端口没人接 | 程序起了吗，端口号对吗，监听的是 `127.0.0.1` 吗 |
| `Connection timed out` | 包根本没到，或中途被丢了 | 安全组、防火墙、IP 对不对 |
| `No route to host` | 路上没有到达它的路径 | 网段、路由、VPN 是否生效 |
| `Network is unreachable` | 本机没有能出去的路 | 网卡、默认网关、VPN |
| `Connection reset by peer` | 对面把连接掐了 | 对端日志，是不是超时或限流 |
| `Broken pipe` | 你在往一根已经断了的管子里写 | 长连接保活，`ServerAliveInterval` |
| `Address already in use` | 这个端口已经有人占了 | `ss -lntp \| grep 端口` |
| `Cannot assign requested address` | 要绑的 IP 不属于这台机器 | `ip addr` 看有没有这个地址 |
| `Name or service not known` | 这个名字解析不出地址 | DNS、拼写、hosts |
| `Could not resolve hostname` | 同上，SSH 的说法 | 同上 |

区分 `refused` 和 `timed out` 是这一类里最重要的一件事。前者说明网络是通的、包到了、只是没人应答；后者说明包根本没到，或者被某个设备半路扔掉。方向完全相反：一个去查服务，一个去查网络。

`Connection reset by peer` 又是另一种：连接建立过，中途被对方掐断。常见原因是对方超时、限流、或者进程崩了。它和 `refused` 的区别是“曾经通过”，所以要去查对方在断开之前发生了什么。

## 22.3 SSH 与权限

这些是登录阶段的问题，和第 8、9、10 章一一对应。

| 原文 | 人话 | 第一步查什么 |
| --- | --- | --- |
| `Permission denied (publickey)` | 你的钥匙没对上服务器上的锁 | 公钥贴了吗，权限 600/700，用户名对吗 |
| `Permission denied (password)` | 密码错，或密码登录被关 | 密码，`PasswordAuthentication` |
| `Host key verification failed` | 这台机器的指纹和我记的不一样 | 是不是重装了，`ssh-keygen -R` |
| `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED` | 同上，警告版 | 先确认，别急着删记录 |
| `Too many authentication failures` | 试了太多把钥匙，被拒 | `IdentitiesOnly yes`，或指定 `-i` |
| `Load key: invalid format` | 私钥文件坏了，或根本不是私钥 | 是不是把 `.pub` 当私钥用了 |
| `UNPROTECTED PRIVATE KEY FILE` | 私钥权限太宽 | `chmod 600 私钥` |
| `sudo: command not found` | 这个用户没有 sudo 权限 | `sudoers`，或者换 root |
| `-bash: xxx: command not found` | 命令没装，或不在 PATH 里 | `which`，装它，或用绝对路径 |
| `Read-only file system` | 磁盘挂载成只读，通常是出错保护 | `df -h`、`dmesg`，多半是磁盘满 |

`Too many authentication failures` 值得单独说一句：很多人把 agent 里存了七八把钥匙，登录时客户端会一把一把地试，超过服务端上限就被拒。解决办法不是删钥匙，而是在 `config` 里写 `IdentitiesOnly yes`，让它只试你指定的那一把。

## 22.4 HTTP 与部署

这一类是“服务已经起来了，但访问不对”，对应第 12、13 章。

| 原文 | 人话 | 第一步查什么 |
| --- | --- | --- |
| `502 Bad Gateway` | 前台连不上后端 | 后端端口、进程状态 |
| `504 Gateway Timeout` | 后端接了但太久没回 | 应用日志，卡在哪个调用 |
| `413 Request Entity Too Large` | 上传的东西超过限制 | `client_max_body_size` |
| `404 Not Found` | 这个路径没东西 | 路由、路径前缀、反代规则 |
| `403 Forbidden` | 有东西，但不给你 | 鉴权、文件权限、WAF |
| `500 Internal Server Error` | 程序自己崩了 | 应用日志里的堆栈 |
| `CORS policy` 相关 | 浏览器不允许跨域请求 | 后端加 `Access-Control-Allow-Origin` |
| `ERR_CONNECTION_REFUSED` | 浏览器版 `Connection refused` | 同第一张表 |
| `SSL_ERROR_RX_RECORD_TOO_LONG` | 用 https 访问了 http 端口 | 换协议，或换端口 |
| `bind() to 0.0.0.0:80 failed` | 80 被别的程序占了 | `ss -lntp \| grep :80` |
| `Job for xxx.service failed` | 服务起不来 | `journalctl -u xxx -n 50` |
| `status=203/EXEC` | 启动命令的路径不对，或没有执行权限 | `ExecStart` 写绝对路径 |

`502` 和 `504` 的区别很实用：502 是“连不上”，504 是“连上了但等太久”。前者查进程和端口，后者查代码里的耗时操作——数据库慢查询、外部接口超时、死循环。

`500` 是最容易被误判的：它看起来像“服务器坏了”，实际上是程序抛了未捕获的异常。去看应用日志的最后一段堆栈，比刷新浏览器有用。

## 22.5 存储与数据库

对象存储的错误码在第 17 章展开过，这里只列最常撞的几个。

| 原文 | 人话 | 第一步查什么 |
| --- | --- | --- |
| `SignatureDoesNotMatch` | 签名算出来不一样 | 密钥、地域、路径编码 |
| `RequestTimeTooSkewed` | 你的时间和服务器差太多 | `date -u`，同步时间 |
| `AccessDenied` | 身份对，权限不够 | 策略里有没有这个操作 |
| `NoSuchBucket` | 桶名不对，或地域不对 | 桶名、地域、endpoint |
| `NoSuchKey` | 对象不存在 | key 拼写、前缀 |
| `Access denied for user` | 数据库账号密码错，或来源 IP 没授权 | 账号、密码、`host` 字段 |
| `Too many connections` | 数据库连接数满了 | 连接池没关，慢查询堆积 |
| `No space left on device` | 磁盘满了 | `df -h`，日志文件 |

`Too many connections` 通常是代码的问题，不是数据库的问题：连接用完没关，或者每次请求都新建一个连接。检查连接池配置，比调大数据库上限更根本。

## 22.6 怎么用这张表

先用报错的第一行去搜，不要只搜“打不开”“连接失败”这种描述感受的词。英文报错是精确的，它指向一个具体的层；中文描述是模糊的，搜到的往往只是同样困惑的人。

如果搜到的结果太多，加上系统名和软件名。`502 nginx ubuntu` 比 `502 怎么解决` 有用得多，前者会把你带到具体的配置项，后者会把你带到论坛里的猜测。

如果完全搜不到，说明这个报错不常见，那就要回到第 13 章那张“十站图”，用排除法定位：从外面往里，一站一站确认哪一站开始不对。报错只是线索，定位靠的是分层。

如果你手上是一个能动手的 agent，也可以直接把报错交给它，让它去查日志、复现、定位。但有两个要求：一是让它**给出依据**——是哪一行日志、哪一条命令的输出支持这个结论，而不是“我觉得是这样”；二是让它在动手之前先说计划，你确认了再改。第 21 章讲的就是这件事：信息可以让它自己查，边界和验收要由你定。
