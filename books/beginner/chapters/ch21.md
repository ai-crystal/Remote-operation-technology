# 怎么向 AI 描述你的环境

> 你给的信息，决定了它给的是答案还是猜测。

## 21.1 一场无效的对话

你：网站打不开了，怎么办。

AI：可能是端口没开，也可能是防火墙，还可能是 DNS 解析问题。你可以先检查一下……

你按它说的试了五个方向，两个小时过去了，还是没好。

这场对话的问题不在 AI。它手里什么信息都没有，只能把常见原因列一遍——而这些原因之所以“常见”，恰恰因为它们是概率最高的那几种，不是你这台机器上真实发生的那一种。这就像一个医生问你哪里不舒服，你说“我不舒服”，他只能从感冒一路查到心脏病。

有效提问的关键不是措辞礼貌，也不是“请一步步思考”这类咒语，而是**把现场搬过去**。

## 21.2 Agent 能替你做多少

现在很多人已经不手敲命令了：装依赖、起服务、配 nginx、看日志、改配置，交给 agent 就行，它比人快，也不会因为手滑打错一个字符。于是很自然会有一个疑问——既然 agent 什么都能做，还有必要懂后端吗？

有必要，但需要的东西变了。

先承认 agent 确实解决了大部分“执行”问题。它能读你的代码，能跑命令，能从报错里找线索，能一次改五个文件。这些事以前要查文档、要试错，现在一句话就行。**如果你把“懂后端”理解成“记得住命令和配置项”，那这部分确实可以被替掉。**

问题在另外三件事上，agent 替不了。

**第一，它不知道你的约束。** 你说“让数据库能被远程访问”，它给你一条把 `bind` 改成 `0.0.0.0` 的方案——技术上完全正确，它也确实解决了你的问题。但它不知道这个数据库里存着用户数据，不知道这台机器在公网上，不知道你们团队有一条“数据库不许暴露”的规范。它只对你的这句话负责，不对后果负责。

**第二，它判断不了“这样算不算正常”。** 服务起来了，日志里有一行 `WARN`，agent 说“可以忽略”。它说得对吗？你得知道那条警告在讲什么，才能判断。同理，它给你一段“优化过”的配置，你得能看出它把超时从 30 秒改成了 300 秒——这不一定是坏事，但要知道自己接受了什么。

**第三，出问题时它看不见现场。** 下一节会讲，它拿到的是你打出来的字，不是你机器上的状态。谁在监听、路由指向哪、证书什么时候过期、磁盘还剩多少，这些得有人去查，或者至少知道该查什么、把结果喂给它。

所以人的角色从“执行者”变成了“验收者”：定目标、给约束、判断结果、承担后果。这四件事没有一件能外包，而它们全都建立在“知道每件事的代价”之上。

| 可以交给 agent | 最好自己懂 |
| --- | --- |
| 查某个命令的参数怎么写 | 这个操作会影响谁、能不能回滚 |
| 生成 nginx / systemd 配置初稿 | 每一行在防什么，删掉会怎样 |
| 读日志、找关键词、给修复建议 | 这条报错属于哪一层，该往哪查 |
| 写部署脚本、批量改文件 | 密钥、权限、数据边界在哪 |
| 解释一段陌生的代码 | 成本会怎么涨，账单从哪来 |

这张表不是要你拒绝 agent，而是划一条线：**执行可以外包，判断不能。**而判断力的来源，恰恰是那些看起来“没用”的原理——为什么绑 `0.0.0.0` 危险、为什么密钥不能进仓库、为什么 502 和 504 要分开看。这些东西不背下来也能查到，但查得到和想得到是两件事：出事的那几分钟里，你没有时间现查。

这也是这本书选择讲原理、而不是讲“点哪里”的原因。命令会过时，agent 会越来越强，但“知道自己在做什么、知道代价在哪”这件事，仍然得由人来完成。

## 21.3 它看不见你的机器

AI 没有你的屏幕，没有你的终端，不知道你在哪台机器上，不知道系统版本，不知道你敲过什么，也拿不到完整的报错。它所有判断都建立在你打的字上。

这件事有一个直接推论：**它给的是“最常见的原因”，而不是“你的原因”**。最常见的原因当然值得先查，但真正卡住你的，常常是那台机器的特殊之处——改过的端口、两份 nginx 配置、装了一半的依赖。这些它看不到，除非你告诉它。

还有一个容易被忽略的限制：上下文窗口。一次对话能装的内容有限，你把几百行日志全贴进去，它反而会丢掉开头那段最关键的信息。所以贴日志要贴对地方：报错的第一行、异常堆栈的最后一行、配置文件里相关的那几行，比整份文件更有用。

## 21.4 一份病历

按下面六项说，通常能省掉十轮来回。

**一，你在哪台机器上。** 本地 Mac 还是云服务器，Ubuntu 22 还是 CentOS 7，是不是在 Docker 里。很多问题的答案跟系统强相关，比如包管理器的名字、防火墙默认状态、`systemd` 有没有。

**二，你想做什么。** 一句话说清目标，比如“让外网能访问部署在服务器 8000 端口的接口”。目标不同，正确做法完全不同：自己用、给同事用、给公网用，是三套方案。

**三，你做了什么。** 给完整的命令，不要概括。把 `sudo systemctl start myapp` 写成“我启动了服务”，信息就丢了——它不知道你用的是 systemd 还是 `nohup`，也不知道服务名。

**四，发生了什么。** 给完整的报错，尤其是第一行和最后一行。第一行说明错误类型，最后一行指出出错位置；中间几十行调用栈大多可以省略，但这两头不能少。

**五，你已经试过什么。** 这一条最省时间，避免它让你重复已经做过的事，也避免它在错误的方向上越走越远。

**六，你的网络位置。** 在家里还是公司，有没有 VPN，是不是通过跳板机。同一个“连不上”，在这三种环境下的原因完全不同。

一个实际的例子：

```text
环境：腾讯云 Ubuntu 22.04，公网 IP 203.0.113.24，家里直连，没有 VPN。
目标：让外网访问 myapp，它监听 127.0.0.1:8000，前面用 nginx 转 443。
做了：systemctl start myapp，nginx -t 通过，systemctl reload nginx。
现象：浏览器访问 https://myapp.com 返回 502，
      nginx error.log: connect() failed (111: Connection refused) while connecting to upstream。
试过：重启 myapp，status 是 active，安全组已放行 443。
```

这段话里的信息足够让懂行的人三十秒内定位：`Connection refused` 说明 nginx 连到了那台机器、但端口上没人接；而 `status` 是 active、安全组也放行了，那就该看后端到底监听在哪个地址、哪个端口。答案往往在 `ss -lntp` 那一行里。

对照一下反例：“我的网站打不开了，nginx 报 502，怎么办。” 这句话里的 502 是真的，但它只说明“nginx 连不上后端”，至于后端是没启动、启动在别的端口、还是被防火墙拦了，全靠猜。

## 21.5 三个能让回答变好的习惯

**先诊断，别急着改。** 加一句“先列出可能的原因，按可能性排序，先不要改代码”。它会给你一个清单，你挑一个去验证。让它直接给新代码，你往往会在没弄清原因的情况下改坏别的东西。

**一次只改一件事。** 同时改三个配置，好了不知道是哪个起的作用，坏了更不知道是哪一步坏的。改一个、验证、再改下一个，虽然慢一点，但每一步都可回退。

**要它给验证方法。** 不要停在“改成这样就好了”，而要“改完之后运行这条命令，输出是这样就说明成功了”。有了验证方法，你才能确认它说对了没有，而不是凭感觉。

这三条其实对应一个原则：**把 AI 当成一个隔着电话的顾问，而不是一个能看见你屏幕的操作员。** 顾问只能根据你描述的症状给判断，你得负责把症状讲准，也得负责验证他的判断。

## 21.6 同一故障，两种问法

拿一个真实的小故障对照一下，差别很直观。

差问法：“服务器上的网站打不开，怎么办。” 拿到的是通用清单：查端口、查防火墙、查 DNS、查 nginx。四项都查了，可能都对，也可能都不对。

好问法：

```text
环境：Ubuntu 22.04 云服务器，公网 IP 203.0.113.24，我在家里直连。
目标：让外网访问 myapp，nginx 监听 443，后端是 127.0.0.1:8000。
做了：昨天还好好的，今天重启了机器，只执行了 reboot，别的没动。
现象：浏览器显示 502，nginx error.log 里是
      connect() failed (111: Connection refused) while connecting to upstream。
试过：nginx -t 通过，systemctl status nginx 是 active。
```

差别不在长度，而在**排除了什么**。好问法里，“昨天还好好的”“只重启了机器”把范围压到“重启之后没起来的东西”；`Connection refused` 说明 nginx 到了、后端没接；“nginx 是 active”排除了代理本身的问题。剩下最可能的就是：后端服务没有设置开机自启，或者启动失败了。

对方（人或 AI）拿到这些信息，可以直接给一条命令：`systemctl status myapp`，再看 `journalctl -u myapp -n 50`。两步就能确认。

写病历的时候可以照这个结构自查：**我的描述有没有排除掉一整个方向？** 如果每一句都可能有好几种解释，那说明信息还不够。

## 21.7 有些话不能照抄

AI 的建议里有一批属于“能解决问题，但代价很大”。它们出现在训练数据里，因为教程里常见，而教程假设你在一个可以随便折腾的沙盒里。

| 它可能会说 | 为什么危险 |
| --- | --- |
| `chmod 777` | 把文件权限对所有人打开，等于拆锁 |
| 把数据库绑到 `0.0.0.0` | 数据库直接暴露在公网，几小时内就会被扫到 |
| 关闭防火墙 | 一句 `systemctl stop firewalld` 能解决很多问题，也会带来很多问题 |
| `curl xxx \| sudo bash` | 用一个陌生脚本以管理员身份执行 |
| `rm -rf $VAR/` | 变量为空时，它会删掉你不想删的东西 |
| 把密钥写进代码 | 一旦提交就泄露，历史里删不干净 |
| 直接改 `sshd_config` 再重启 | 改错了就再也登不进去 |
| `--privileged` 跑容器 | 容器里的程序拿到了宿主机的权限 |

遇到这类建议，追问一句“有没有更安全的做法，只开放需要的那一部分”。大部分时候有：给目录而不是给整个盘、给单个桶而不是给整个账号、只放行一个来源 IP 而不是所有人。

还有一类建议要小心：**让你直接在生产环境上试**。正确的顺序永远是先在测试环境验证，再上生产；先备份，再改动；先能回滚，再动手。

## 21.8 一个反向的用法

你也可以让 AI 帮你检查，而不是替你决定。

把当前的配置贴给它，问“这里面有没有安全隐患”；把自己的排查思路讲一遍，问“这个顺序有没有问题”；把一段日志给它，问“这段日志里有哪些异常”。这类任务不依赖它能否连上你的机器，而它的训练数据里这类模式非常密集，所以做得不错。

区别在于：让它**审查**，你保留判断；让它**代做**，你要能看懂它做了什么。前者是加速，后者是赌博。
