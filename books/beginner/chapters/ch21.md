# 怎么向 AI 描述你的环境

> 你给的信息，决定了它给的是答案还是猜测。

## 21.1 一场无效的对话

你：网站打不开了，怎么办。

AI：可能是端口没开，也可能是防火墙，还可能是 DNS 解析问题。你可以先检查一下……

你按它说的试了五个方向，两个小时过去了，还是没好。

这场对话的问题不在 AI。它手里什么信息都没有，只能把常见原因列一遍——而这些原因之所以“常见”，恰恰因为它们是概率最高的那几种，不是你这台机器上真实发生的那一种。这就像一个医生问你哪里不舒服，你说“我不舒服”，他只能从感冒一路查到心脏病。

现在的工具已经不止一种。有的只能聊天，你得把现场描述给它；有的能直接执行命令、读日志、改配置，它能自己去看现场。这两种情况下“怎么说话”完全不一样：前者你要把信息喂全，后者你要把**目标和边界**说清，然后放手。这一章两种都讲，重点在后一种，因为它正在变成主流，也更容易出事。

## 21.2 Agent 能替你做多少

先承认，能动手的 agent 解决了一大块问题：装依赖、起服务、配 nginx、读日志、批量改文件，它比人快，也不会因为手滑打错一个字符。**如果你把“懂后端”理解成“记得住命令和配置项”，那这部分确实可以被替掉。**

问题在另外三件事上，它替不了。

**第一，它不知道你的约束。** 你说“让数据库能被远程访问”，它给你一条把 `bind` 改成 `0.0.0.0` 的方案——技术上完全正确，你的问题也确实解决了。但它不知道这个库里存着用户数据，不知道这台机器在公网上，不知道你们团队有一条“数据库不许暴露”的规范。它只对这句话负责，不对后果负责。

**第二，它判断不了“这样算不算正常”。** 服务起来了，日志里有一行 `WARN`，它说“可以忽略”。它说得对吗？你得知道那条警告在讲什么，才能判断。同理，它给你一段“优化过”的配置，把超时从 30 秒改成 300 秒——不一定是坏事，但你要知道自己接受了什么。

**第三，它不为后果负责。** 它可以在三秒内删掉一个目录，也可以在十分钟里开出一个对公网的端口。它做得又快又对，只是“对”的标准是它理解的那个目标，不包括账单、合规和别人的工作。

所以人的角色从“执行者”变成了“验收者”：定目标、给边界、判断结果、承担后果。这四件事没有一件能外包，而它们全都建立在“知道每件事的代价”之上。

| 可以交给 agent | 最好自己懂 |
| --- | --- |
| 查某个命令的参数怎么写 | 这个操作会影响谁、能不能回滚 |
| 生成 nginx / systemd 配置初稿 | 每一行在防什么，删掉会怎样 |
| 读日志、找关键词、给修复建议 | 这条报错属于哪一层，该往哪查 |
| 写部署脚本、批量改文件 | 密钥、权限、数据边界在哪 |
| 解释一段陌生的代码 | 成本会怎么涨，账单从哪来 |

这张表不是要你拒绝 agent，而是划一条线：**执行可以外包，判断不能。**

## 21.3 它看得见什么，看不见什么

很多人对 AI 的印象还停留在“它看不见你的机器”，这个说法今天已经过时了。

先要弄清一件常被忽略的事：**agent 本身也跑在某台机器上**。它可能装在你的电脑里，也可能跑在服务器上，或者是云端的服务。它“能看见什么”，取决于两件事——进程跑在哪里，以及你把哪些访问权限交给了它。

权限给够的话，它能执行 shell、读写文件、`ssh` 上服务器、`curl` 接口、读 `journalctl`、改配置、重启服务，甚至调云厂商的 API 改安全组。它看到的东西不比你手动敲命令时少，很多时候还更多，因为它会一次把相关日志全捞出来。但“`journalctl` 读的是哪台机器的日志”“`ssh` 登上去的是哪台服务器”，都由你给的配置决定；配置含糊，它就会在错误的机器上查半天，还很自信。

但“能看见”是有条件的，这些条件决定了它会在哪里出错。

**第一，它只看得到你授权它看的部分。** agent 的权限是给定的：哪个目录可读、哪台机器能连、哪个云账号的密钥能用。没给的部分它真的看不见——不是它偷懒，是访问不到。所以“它能访问”和“它能访问全部”是两件事，而你不知道自己少给了什么时，它给的答案就会缺一块。

**第二，它看到的是某一刻的状态。** 它查完到你决策之间，状态可能已经变了；它读到的日志可能刚好被轮转；你在另一个窗口刚改过的配置，它不知道。它不会主动怀疑“我看到的可能已经过时了”，除非你要求它每次都重新确认。

**第三，它看不到你的意图和约束。** 预算、合规、团队规范、这台机器上还跑着谁的服务、这次改动背后的业务原因——这些不在文件系统里，也不在日志里，只在你脑子里。你不说，它就按“最常见、最省事”的做法来。

**第四，它看不到间接后果。** 改一条 nginx 规则，可能让另一个站点 404；删掉“临时文件”，可能是别人正在用的输入；开一个端口，可能带来账单和扫描。这些后果不在它的视野里，因为它只看到了你交给它的那个局部。

最危险的转变在这里：**聊天式 AI 答错，你还能过滤；agent 答错，它会直接做。** 从“说错”到“做错”，速度快、影响面大，而且很多操作不可逆。所以问题不再是“怎么把现场描述清楚”，而是“给多少权限、给什么约束、怎么验收、怎么回滚”。

## 21.4 怎么给 agent 派活

给聊天式 AI 提问要“喂信息”，给 agent 派活要“立规矩”。六件事说清楚，比写一大段背景有用。

**目标。** 一句话，可验证。不是“优化一下部署”，而是“让外网能通过 `https://myapp.com` 访问 8000 端口上的服务”。

**验收标准。** 怎么算成功，最好是一条命令加预期输出。比如“`curl -I https://myapp.com` 返回 200”。

**边界。** 明确不许动什么：不许改防火墙、不许开公网端口、不许碰 `/data` 以外的目录、不许重启数据库。边界比目标更重要，因为目标决定它往哪走，边界决定它不会走到哪。下一节会把这几条逐个拆开讲。

**回滚。** 改之前先备份或打快照，并写清怎么退回去。没有回滚方案的操作，应该先停下来。

**范围。** 哪台机器、哪个账号、哪个目录、哪个环境。生产还是测试，这一条必须说死。

**汇报格式。** 做完之后你要看到什么：改了哪些文件、执行了哪些命令、怎么验证的、还剩什么风险。有了这个要求，它就不会只回一句“已完成”。

一个实际的派活例子：

```text
目标：让外网通过 https://myapp.com 访问 8000 端口上的 myapp。
边界：不改防火墙规则；不把 myapp 绑到 0.0.0.0；不动 /data 目录；
      不改 sshd 配置；不重启数据库。
做法：检查 nginx 配置与 systemd 服务状态，缺什么补什么，改动前备份。
验收：curl -I https://myapp.com 返回 200，且 systemctl status myapp 是 active。
回滚：改动前把 nginx 配置复制到 /root/backup/，失败就还原并 reload。
汇报：列出改动的文件、执行的命令、验证输出、遗留风险。
```

这段话里没有一句技术细节，但一个合格的 agent 拿到它就能干活，而且不容易干出界。对比一下“帮我把网站弄上线”——目标模糊、没有边界、没有验收、没有回滚，它能做的只有猜，而猜错的代价由你承担。

### 21.4.1 那五条边界分别在挡什么

上面那五条看起来像套话，其实每一条都对应一类真实的事故。逐条说清楚，你就知道自己的项目该写哪几条。

**不改防火墙规则。** 目标只是让 443 通，但 agent 发现后端连不上，顺手把安全组的 8000 对 `0.0.0.0` 打开“验证一下”，验证完忘了关。第 6 章讲过，安全组和系统防火墙默认都是“进来的拒绝”，一旦打开就是对全网开放；几小时内就会有扫描器找上门。它做的每一步都符合“让服务能访问”这个目标，只是代价不在目标里。这里说的“防火墙”其实是两层，位置不同：**安全组**在云控制台的网页里（或云 API），**`ufw`/`iptables`** 在服务器上。两者都要管，少了哪一层都可能通或不通。正确的说法是：只允许它**读**这两处的现状（服务器上的 `ufw status`、`iptables -L -n`，控制台里的安全组规则），要改必须先报告“改哪一层、哪条规则、开给谁、开多久”。

**不把 myapp 绑到 `0.0.0.0`。** agent 看到 502，第一反应常是把后端从 `127.0.0.1` 改成 `0.0.0.0`，让 nginx“能连上”。可 nginx 和它跑在同一台机器上，`127.0.0.1` 本来就够用；改成 `0.0.0.0` 等于让公网绕过 nginx 直接访问应用（第 3 章）。后果是 TLS 被绕过、访问日志丢失、限流失效，应用直接暴露在扫描器面前。正确的说法是：让它**核对** nginx 的 `proxy_pass` 地址和后端实际监听是否一致，而不是改监听地址。

**不动 `/data` 目录。** 有两种常见的“好心办坏事”：为了清理空间删掉 `*.tmp` 或 `cache/`，其中可能有别人正在用的中间结果；为了“解决权限”执行 `chmod -R 777 /data`，把数据目录对所有人打开。数据目录往往没有版本控制，备份也可能是几天前的。正确的说法是：**只读**；删除类操作必须先列出文件清单让你确认；权限问题只改具体文件，不做递归。

**不改 `sshd_config`。** 为了“让连接更稳”，agent 改一个参数，`reload` 之后新连接全部被拒；此时你手上那个会话一旦断开，就再也进不去（第 8、10 章）。这类操作的特点是“改的时候感觉不到，改完才发现门锁死了”。正确的说法是：允许它**读取并给出 diff 建议**，由人来改；改之前保留一个已登录的会话，改完先 `sshd -t` 校验，再 reload。

**不重启数据库。** agent 觉得“重启一下也许就好”，结果连接池里几十个请求同时失败、未提交的事务被回滚、主从延迟拉大；如果是生产库，影响的是所有用户，而不只是你正在调的那个页面。正确的说法是：允许它查 `SHOW PROCESSLIST`、看慢查询日志、看连接数；重启必须单独授权，并且选在维护窗口。

把这五条抽象一下，边界其实分三类：

| 类别 | 例子 | 该怎么写 |
| --- | --- | --- |
| 可以读 | 日志、配置、进程状态、端口监听 | 随便看，鼓励它多查 |
| 可以改（白名单） | `/etc/nginx/conf.d/myapp.conf`、`/srv/myapp` | 改前备份、改后验证、只动这些路径 |
| 不许动（红线） | 防火墙、`sshd_config`、`/data`、数据库服务 | 只报告，不动手，等你决定 |

写边界的关键是**具体到对象**。“别乱动”没有用，因为它不知道自己算不算乱动；“不改 `/etc/nginx/nginx.conf`，可以改 `/etc/nginx/conf.d/` 下与 myapp 相关的文件，改前备份到 `/root/backup/`”才有用。同理，“别删东西”不如“删除任何文件前，先把清单发给我确认”。

还有一点：边界不是不信任 agent，而是承认**它没有你的上下文**。它不知道 `/data` 里存的是三个月的训练结果，也不知道这台数据库还在给另一个团队用。你把这些写在边界里，它就能在正确的范围内发挥——这比事后追责有用得多。

## 21.5 三个能让结果变好的习惯

**先诊断，再动手。** 加一句“先说明你打算做什么、为什么，等我确认再执行”。对能动手的 agent，这一步等于给它一个刹车：它会把计划摊开，你能在它改坏东西之前叫停。

**一次只改一件事。** 同时改三个配置，好了不知道是哪个起的作用，坏了更不知道是哪一步坏的。改一个、验证、再改下一个，虽然慢一点，但每一步都可回退。

**要验证方法，也要回滚方案。** 不要停在“改成这样就好了”，而要“改完之后运行这条命令，输出是这样就说明成功了”；再加一句“如果失败，怎么退回去”。这两句话能把“它说做完了”变成“你能确认做对了”。

这三条其实对应一个原则：**把 agent 当成一个能干但不知道你底线的新同事，而不是一个能读心的助手。** 他会干活，也会自作主张；你的责任是把边界划清、把结果验收。

## 21.6 同一件事，两种说法

拿一个真实的小故障对照一下。

只聊天时，你得这样问：“Ubuntu 22.04，公网 IP 203.0.113.24，家里直连。目标让外网访问 myapp，nginx 监听 443，后端 127.0.0.1:8000。昨天还好好的，今天重启了机器，只执行了 reboot。浏览器 502，nginx error.log 是 `connect() failed (111: Connection refused) while connecting to upstream`。nginx -t 通过，nginx 是 active。”

这段话的信息密度很高，因为对方看不到你的机器，你得替它看。

换成能动手的 agent，同一件事可以这样说：“服务器 203.0.113.24，重启后 myapp 502，nginx 日志里是 connection refused。查一下原因并修复。不要改 nginx 配置，不要动安全组和 ufw，改完用 `curl -I` 验证。”

区别在于：**信息让它自己查，边界由你给。** 你不需要替它 `ss -lntp`，但你需要告诉它“别动 nginx”“别碰防火墙”——因为这两样它本来有能力改，而改错了代价很大。

## 21.7 有些话不能照抄

AI 的建议里有一批属于“能解决问题，但代价很大”。它们出现在训练数据里，因为教程里常见，而教程假设你在一个可以随便折腾的沙盒里。对能动手的 agent，这类建议的风险要再乘一个系数：它不只是说说，它会去做。

| 它可能会说 | 为什么危险 |
| --- | --- |
| `chmod 777` | 把文件权限对所有人打开，等于拆锁 |
| 把数据库绑到 `0.0.0.0` | 数据库直接暴露在公网，几小时内就会被扫到 |
| 关闭防火墙 | 一句 `ufw disable`（或 `systemctl stop firewalld`）能解决很多问题，也会带来很多问题 |
| `curl xxx \| sudo bash` | 用一个陌生脚本以管理员身份执行 |
| `rm -rf $VAR/` | 变量为空时，它会删掉你不想删的东西 |
| 把密钥写进代码 | 一旦提交就泄露，历史里删不干净 |
| 直接改 `sshd_config` 再重启 | 改错了就再也登不进去 |
| `--privileged` 跑容器 | 容器里的程序拿到了宿主机的权限 |

遇到这类建议，追问一句“有没有更安全的做法，只开放需要的那一部分”。大部分时候有：给目录而不是给整个盘、给单个桶而不是给整个账号、只放行一个来源 IP 而不是所有人。

还有一类要小心：**让你直接在生产环境上试**。正确的顺序永远是先在测试环境验证，再上生产；先备份，再改动；先能回滚，再动手。

## 21.8 让它审查，你保留判断

你也可以让 AI 帮你检查，而不是替你决定。

把当前的配置贴给它，问“这里面有没有安全隐患”；把自己的排查思路讲一遍，问“这个顺序有没有问题”；把一段日志给它，问“这段日志里有哪些异常”。这类任务不依赖它能否连上你的机器，而它的训练数据里这类模式非常密集，所以做得不错。

区别在于：让它**审查**，你保留判断；让它**代做**，你要能看懂它做了什么。前者是加速，后者是赌博。
