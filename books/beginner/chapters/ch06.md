# 门禁和海关

> 机器里的防火墙管房门，云平台的安全组管小区大门。

## 6.1 明明开了端口

你在自己电脑的终端里 `ssh` 登录到服务器，在那儿把程序跑起来。`ss -lntp` 看到 `0.0.0.0:8000` 在监听，说明服务器上确实有人在这个端口等着。

然后你回到自己电脑的浏览器，输入 `http://203.0.113.24:8000`。转了很久，最后说无法访问。

你打开云厂商的控制台。那是一个网页，不是服务器，你登录的是云平台的账号，不是那台机器。找到安全组，加一条规则允许 8000 端口，保存。回来再试，还是不行。这时候大多数人会开始改代码。改代码没用，因为请求根本没到程序那里。

## 6.2 三道门

先把谁在哪儿摆清楚。程序跑在服务器上，是你的 `ssh` 会话启动的。浏览器在你自己的电脑上。云厂商的控制台是一个网页，你在上面点出来的规则，作用在服务器外面那一层。

一个请求要从你的浏览器走到那个程序，路上要穿过三道门，而且这三道门都在服务器这一端（不是你的电脑），后一道管安全组，在服务器外面；前两道在服务器里面。它们由三个不同的地方管，配错了任何一道，结果看起来都一样，都是连不上。这是新手最容易被绕晕的地方。

![图 6-1　一个请求要穿过三道门才能碰到程序](../images/06/fig06_1.png)

第一道是安全组。它在服务器外面，是云平台提供的虚拟防火墙。你在网页上点点鼠标就能改，服务器里的任何命令都看不到它。很多人压根不知道它的存在，所以他们会在服务器里折腾半天，而问题在外面。

第二道是系统防火墙。这是装在服务器里的软件，Ubuntu 上通常是 ufw，CentOS 和 Rocky 上是 firewalld。它默认可能是关的，也可能是开的，取决于你用的镜像。

第三道是程序自己。跑在服务器上的那个进程得在端口上监听，还得绑对地址，上一章讲的就是这件事。

还有一种情况，这三道门前面还站着一个人。它不看该不该放行，只负责把包头里的地址换掉。很多“端口明明开了却进不来”的怪事，卡在它身上。下一节说这件事。

## 6.3 默认是关的

这三道门有一个共同的默认姿势，进来的拒绝，出去的允许。这个设计很合理。你从服务器上下载一个包，那是出去，一路畅通。别人想连进来，得你明确允许。因为服务器上跑的东西太多了，默认全开等于自杀。

所以“我什么都没配，为什么连不上”从来不是故障，那是正常工作状态。你要做的是明确地开一条缝。下面这几条在服务器上敲。

```bash
# Ubuntu
sudo ufw allow 8000/tcp
sudo ufw status

# CentOS / Rocky
sudo firewall-cmd --add-port=8000/tcp --permanent
sudo firewall-cmd --reload
```

云平台那边，去控制台找到这台机器的安全组，加一条入站规则，协议 TCP，端口 8000，来源填 `0.0.0.0/0` 表示所有人，填你自己的 IP 表示只有你能进。来源写自己的 IP 是个好习惯，调试期间尤其推荐。等你确认没问题了，再考虑放开。

## 6.4 为什么有人让你“在防火墙上做 NAT”

一个真实的场景。你在腾讯云上租了一台机器，想开一个 8080 端口给外面用，流程走到网络这一块，负责的同事回了两句话。一句是在腾讯云的安全组里开，另一句是咱们这边的防火墙上做 NAT。

第一句你能懂，第二句不知所云。NAT 这个词你在第一章见过，那会儿它是小区门卫帮你代收快递。怎么开个端口又扯上它了。

因为对方说的是两件事。安全组负责放行，NAT 负责改地址。这两件事在不同的设备上做，缺一件都不行。

### 6.4.1 过滤和改写

安全组和防火墙做的是过滤，看这个包该不该进来。它们只看，不改。NAT 做的是改写，把包头里的地址换成另一个，让包能送到别处。它不判断该不该放，只管送到哪。

一个包要进门，这两件事都得有人做。放行了但没人改写，包到了门口不知道往里送。改写完了但没放行，换个地址照样被丢掉。

### 6.4.2 NAT 有两个方向

第一章讲的 NAT 是出门那个方向。你家电脑发给外面的包，源地址被换成公网地址，回信再换回来。这样外面只看见一个地址，家里十台设备共用。这叫 SNAT，换的是源地址。

开端口遇到的是反方向。外面的人只知道你有一个公网地址，不知道服务器在机房里的 `10.0.0.9`。中间那台设备要做的是，把访问 `203.0.113.24:8080` 的包，目的地址改写成 `10.0.0.9:8080`，送进去，回程再改回来。这叫 DNAT，换的是目的地址。日常说话里它还有两个更常见的名字，端口映射和端口转发。

![图 6-2　NAT 只改包头里的地址，包里的内容不动](../images/06/fig06_2.png)

### 6.4.3 什么时候会轮到 NAT

两种情况。一种是服务器没有公网 IP。腾讯云的机器可以只放在私有网络里，不绑公网地址，外面根本找不到它。要让它被访问，要么给它绑一个弹性公网 IP，让它自己有个门牌；要么让 NAT 网关替它出面，用网关的公网地址加一条映射。

另一种是访问必须经过单位的出口。有些单位用专线把云上机房和办公室连起来，外面的人访问时先到单位的公网地址，再由单位出口的防火墙转进去。这条映射写在单位的防火墙上，腾讯云的控制台里看不到。

你听到的那句多半是第二种情况。翻译过来是，你那台机器躲在某个公网地址后面，需要有人加一条映射，把门牌指出来。

### 6.4.4 谁也管什么

| 环节 | 在哪配 | 管什么 |
| --- | --- | --- |
| 安全组 | 腾讯云控制台，实例级 | 放不放行，按协议、端口、来源 IP 过滤 |
| 网络 ACL | 腾讯云控制台，子网级 | 同样是过滤，少动，容易和安全组打架 |
| NAT 网关 | 腾讯云控制台，私有网络级 | 没有公网 IP 的机器怎么出去、怎么被访问 |
| 弹性公网 IP | 腾讯云控制台 | 直接给机器一个公网地址，这时不需要 NAT |
| 系统防火墙 | 机器里，ufw 或 firewalld | 机器自己这一层放不放行 |
| 程序监听 | 机器里 | 有没有人在这个端口上等 |

各家云叫法不同，阿里云也叫安全组，AWS 叫 Security Group，私有网络 AWS 叫 VPC。名字不一样，位置和职责是一样的。

### 6.4.5 找人开端口时怎么说

把这几件事一次讲清，来回能省几天。一，谁访问。是公网所有人，还是只限某个网段、某个固定 IP。二，从哪进。别人访问的公网地址和端口是多少，对方手上有没有闲置的地址。三，送到哪。机器的内网地址和端口是多少，这个在控制台的实例详情里能抄到。四，什么协议。TCP、UDP，还是两个都要。只写端口不写协议，是最常见的返工原因。五，开多久。临时调试，还是长期保留。六，要不要域名。挂域名涉及备案，备案不在这条链路上，但它会卡在最后一步。

### 6.4.6 几个容易混的地方

有人以为安全组开了就能用。其实如果机器没有公网 IP，光开安全组没有用，因为外面没有任何地址能到达它。

有人以为 NAT 和安全组是一回事。其实一个是改写地址，一个是决定放行，经常是两拨人、两个系统在管。

有人以为做了端口映射，服务器自己的防火墙就不用管了。其实映射只负责把包送到机器，机器里的防火墙照样会拦，程序没起也照样没人应答。

有人以为只开 TCP 就够了。其实有些服务走 UDP，比如语音、游戏、部分 DNS，只开 TCP 会表现得时好时坏。

下次再听到“做 NAT”，先问一句，是给哪台机器做映射，用哪个公网地址。答案通常就在这两句话里。

## 6.5 排查要按顺序

乱试是最慢的办法。按顺序来，通常三步就能定位。

```bash
# 第一步，程序在听吗，听在哪个地址（在服务器上）
ss -lntp | grep 8000

# 第二步，本机能连上吗，这一句绕过了所有防火墙（还是在这台服务器上）
curl -v http://127.0.0.1:8000

# 第三步，从外面测一次（回到你自己的电脑，换个窗口）
nc -vz 203.0.113.24 8000
```

三步不在同一台机器上，前两步在服务器，第三步在你自己的电脑。如果你图省事在那个 SSH 窗口里把三条一起敲了，第三步测的还是服务器自己连自己，等于没测。如果机器根本没有公网 IP，第三步无从谈起，先回到上一节，确认有没有人给它做过映射。第一步没有输出，说明程序没起来或者端口写错了，跟网络无关，回去看日志。第一步有，第二步失败，说明程序在听但处理有问题，或者绑的地址不对，去看应用日志。

前两步都成，第三步失败，那就是两道防火墙其中之一。这时候先进机器里看 ufw 或 firewalld 的状态，再上控制台看安全组。

这个顺序的价值在于它从里往外，每一步都能排除掉一批可能。反过来从外往里试，你会在无数个变量之间来回猜。

## 6.6 那些看起来一样、原因不同的坑

| 现象 | 常见原因 |
| --- | --- |
| 改了安全组还是不通 | 规则没保存，或者加在了另一个安全组上，机器挂的不是那个 |
| 只有某些人能访问 | 来源 IP 写成了某一个固定地址 |
| 昨天还好今天不行 | 用了按量计费的公网 IP，重启后地址变了 |
| 服务器自己能通，内网另一台机器不通 | 系统防火墙开着，只放行了回环 |
| 怎么都超时，但端口确实开着 | 前面挡了一层 CDN 或 WAF，请求没到这台机器 |
| IPv4 通，IPv6 不通 | 只加了 IPv4 的规则 |

还有两个很容易忽略的。一个是协议选错，安全组里选了 UDP，程序却在用 TCP，这两者不通。另一个是改了防火墙没重载，`firewall-cmd` 不加 `--permanent` 的重启就没了，加了 `--permanent` 不 `--reload` 就不生效。

## 6.7 一个心态上的建议

遇到“连不上”，先别改代码。网络问题的特点是分层，每一层都能独立地把事情搞坏。你要做的是先确定断点在哪一层，再在那个层里找原因。改代码是最靠后的手段，因为代码只在最后一层。

这也是为什么第十三章那张图值得反复看。那张图画的就是这条链路，你排查的时候其实是在上面找第一个断开的箭头。

> **这一章记住一句**
>
> 连不上先分层，别一上来就改代码。
