# 403 的一百种死法

> 403 不是“你没权限”这么简单，它是“服务器算出来的结果和你给的对不上”。

## 17.1 在自己电脑上好好的，到服务器就 403

代码在本地跑得好好的，能上传能下载。部署到服务器上，每一个请求都返回 403。你把密钥复制了三遍，确认没有多余的空格；把权限策略翻了一遍，是全权限；又换了一把新密钥，还是 403。你开始怀疑是云厂商的问题。

这类问题在对象存储上极其常见，因为它的鉴权机制比“用户名加密码”复杂一层：它不是核对一个密码，而是要求你和服务器各自独立算出同一个值，再比对。任何一个输入不同，值就不同，结果就是 403。

这也解释了为什么它“只在服务器上出现”：本地和服务器之间，环境变量的值、系统时间、地域配置、甚至请求头，都可能有一处细微差别。local 能过，说明逻辑没错；服务器过不了，说明有某个输入不一样。

## 17.2 三个码不要混

**401** 是“你没告诉我你是谁”：没带凭证，或者令牌已经过期。

**403** 是“我知道你是谁，但你不能做这件事”：身份是对的，权限或签名不对。

**404** 是“这里没有这个东西”。

对象存储有时候会用 403 代替 404，故意不告诉你某个文件到底存不存在——否则别人就能拿它来探测你的桶里有什么。所以看到 403 不要立刻断定是权限问题，也可能是 key 写错了。

还有一个容易混的：**400** 通常表示请求本身格式不对，比如请求头不合法、参数缺失。它和 403 的排查方向完全不同，看到 400 先去检查代码拼的请求，而不是权限。

## 17.3 签名是怎么算的

对象存储不用密码，用签名。过程可以拆成四步。第一步，把你这次请求的要素按固定规则整理成一段文本：请求方法、路径、查询参数、参与签名的请求头、请求体的哈希。这一步叫“规范化”，目的是让不同语言、不同库算出的结果一致。

第二步，把这段文本的哈希，连同算法名、时间戳、凭据范围（哪一天、哪个地域、哪个服务）拼成“待签字符串”。

第三步，从你的密钥派生出签名密钥：用日期派生一次，再用地域派生一次，再用服务名派生一次，最后加一个固定后缀。这样同一个密钥在不同日期、不同地域算出的签名密钥都不同。第四步，用派生出的密钥对待签字符串做一次 HMAC，得到最终的签名，附在请求头或 URL 里。

服务器收到请求后，用同样的四步再算一遍，两边一致就放行。所以关键在于“同样的方法”：任何一个输入不同，结果就完全不同。

## 17.4 八种常见原因

| 出错的地方 | 表现 | 怎么查 |
| --- | --- | --- |
| 密钥写错或有多余空格 | `SignatureDoesNotMatch` | 打印长度，看首尾是否有空白或换行 |
| 运行代码那台机器时间不准 | `RequestTimeTooSkewed` | 在**服务器**上 `date -u` 看 UTC，差超过十五分钟就不行 |
| 地域或 endpoint 写错 | 连接失败或签名不符 | 核对桶在哪个地域、用的是公网还是内网域名 |
| key 里有中文或空格 | 签名不符或 404 | 确认编码方式一致，必要时先做 URL 编码 |
| 请求头被中间层改过 | 签名不符 | 看 nginx 是否改写了头，或加了额外头部 |
| 权限策略没给这个操作 | `AccessDenied` | 看策略里有没有对应的 `s3:GetObject` 之类的动作 |
| 桶名写错 | `NoSuchBucket`，有时是 403 | 复制粘贴核对，注意别把 APPID 漏了 |
| 用了临时凭证但没带 token | `AccessDenied` 或签名错 | 三个值（ID、Key、Token）必须一起用 |

这张表建议收藏。遇到 403 先在里面找对应的错误码，比搜“403 怎么解决”有用得多。

## 17.5 那个关于时间的故事

有一类 403 特别有意思：只在服务器上出现，本地永远复现不了。原因是服务器的系统时间和真实时间差了十几分钟。

签名里带时间戳，服务端允许的偏差通常是十五分钟。超过这个范围，它会认为这个请求是“旧的”，可能是被重放的，直接拒绝，错误码是 `RequestTimeTooSkewed`。所以你本地时间准、服务器时间飘，就会出现“同一份代码，本地能跑、服务器 403”。

为什么服务器时间会不准？虚拟机暂停后恢复、长时间高负载、时钟同步服务没开，都会导致漂移。云厂商一般默认开启同步，但有些精简镜像把 `systemd-timesyncd` 或 `chronyd` 关掉了。

下面两条都在**服务器**上敲（不要在你自己电脑上敲，你的电脑时间多半是准的）：

```bash
date -u                                  # 看服务器 UTC 时间，和你本机时间对一下
sudo systemctl restart systemd-timesyncd  # 重启时间同步
```

这一条能解决相当一部分“莫名其妙的 403”，尤其是那种重启之后好了、过几天又出现的。

## 17.6 排查顺序

不要一上来就改权限策略，那是最后一步。按下面的顺序，通常前三步就能定位。

**第一步，用最小可复现的例子。** 官方 SDK 的示例代码，只改密钥、桶名、地域，在**返回 403 的那台服务器**上跑一次——在本机跑没有意义，因为本章开头就说了“本地好好的，服务器才 403”，本机成功只能证明代码逻辑没错，证明不了服务器的配置。能通，说明你的代码有问题；不能通，说明服务器上的环境或凭证有问题。这一步就把范围砍掉一半。

**第二步，看具体的错误码。** 403 只是一个类别，真正的信息在响应体里，有一个 `Code` 字段。把那个字段拿去搜，比搜 403 精确一百倍。

**第三步，对时间。** 一条命令的事，先排除掉。

**第四步，对地域和 endpoint。** 桶在广州，你连的是上海，签名必然对不上。跨地域复制代码时最常见的错就是这个。

**第五步，才去看权限策略。** 策略里要分清“桶级操作”和“对象级操作”：列目录是 `ListBucket`，读文件是 `GetObject`，两者是不同权限。只给了前者，能列出文件名却下载不了，表现就是“看得到、拿不到”。

## 17.7 一个习惯

遇到 403 的时候，先把响应体完整打印出来。

```python
try:
    client.get_object(Bucket="myapp-1250000000", Key="cat.jpg")
except Exception as e:
    print(e)
    print(getattr(e, "response", None))
```

大部分 SDK 的异常对象里带着服务端返回的原始内容，里面有错误码、请求 ID，甚至一句人话解释。请求 ID 还能拿去问厂商的技术支持，对方一查就知道这次请求发生了什么。

很多人只看到“403 Forbidden”就开始猜，其实答案就在下面几行里，只是被异常处理吞掉了。

## 17.8 怎么少遇到

事后排查不如事前预防。三件事能挡掉大部分问题：把桶名、地域、endpoint 写进配置文件而不是散落在代码里；在启动时做一次“自检请求”（列一下桶，或者读一个已知的小对象），不通就直接拒绝启动，别等到用户上传时才报错；对 401 和 403 的比例做监控，突然升高通常意味着密钥轮换出了问题，或者有人在外面扫你的桶。

>
> 403 先看错误码，再看时间，最后才看权限。
