# 安全边界：中间人、越权与最小权限

## 6.1 先把威胁模型写下来

“安全”不是一个可以打勾的状态。谈安全之前，先回答四个问题：

- 我要保护什么：登录凭证、用户数据、计算结果、服务器本身
- 谁会来攻击：路过的扫描器、同网段的邻居、被钓鱼的员工、拿到一枚密钥的外部人
- 攻击者能站在哪里：公网、内网、服务器上、供应链里
- 最坏会怎样：数据被读走、被改、被删，还是资源被拿去挖矿；发现之后能不能止血

前三问决定该防什么，第四问决定值多少投入。没有威胁模型的“加固”，往往只是加了几个配置项，真正的入口还开着。

把四个问题写成句子，比列一堆缩写有用。比如：“一个能访问公网的扫描器，可能通过暴露的调试端口读到数据库快照；一旦读到，里面是全部用户的手机号，我们需要在十分钟内定位并轮换凭据。”这句话里已经包含了资产、对手、入口、影响和响应动作，可以直接推导出待办：关调试端口、给快照加密、准备凭据轮换流程。

回答“攻击者能站在哪里”时，画一张信任边界图最省事。图上每一个“跨过去”的位置都是一个检查点。

```text
  internet
     |
     |  boundary A: TLS terminates, public input arrives
  [ cdn ]
     |
  [ load balancer ]
     |
     |  boundary B: shared network, no tenant isolation
  [ app server ] ----- [ cache ]
     |
     |  boundary C: data plane, credentials live here
  [ database ]
     |
  [ backup bucket ]   boundary D: long-lived copies
```

图上的每条线都要有答案：谁能通过、凭什么通过、通过之后留下什么记录。表 6-1 把四问展开成可检查的清单。

表 6-1　威胁模型的四个问题与落地动作

| 问题 | 要写下的内容 | 对应的动作 |
|---|---|---|
| 保护什么 | 资产清单与价值排序 | 给高价值资产单独划边界、单独加密、单独审计 |
| 谁来攻击 | 对手的能力与动机 | 决定要不要防“有耐心的定向攻击” |
| 站在哪里 | 信任边界图与入口清单 | 每个边界配一套认证与限流 |
| 最坏怎样 | 影响面与止损时间 | 备份、快照隔离、凭据轮换预案 |

威胁模型会过期。上新功能、接入新供应商、把服务从自建机房搬到云上，边界都变了。比较省事的维护方式是把它挂在架构图旁边，改架构时一起改，而不是等出事之后再补。

## 6.2 中间人：三种防线

中间人的位置很尴尬也很强大：他在你和服务器之间，可以转发、可以改、可以伪造。

防线有三层：

- **加密**：让内容不可读。这挡不住篡改，但让窃听失去意义
- **认证**：确认对面是谁。SSH 用主机密钥与指纹，HTTPS 用证书
- **绑定**：把“这次连接”和“这次认证”绑在一起，比如签名里带上会话标识与交换哈希

三层缺一层都有问题：只加密不认证，中间人可以冒充服务器；只认证不绑定，攻击者可以把一次握手的材料搬到另一次连接里重用。

具体到协议，绑定是怎么做的。TLS 1.3 的握手会对整个握手记录做一次哈希，密钥确认消息覆盖这段哈希，所以中间人只要改动过任何一个握手字段（比如删掉某个扩展、把密钥交换参数换成自己的），两端算出的值就对不上，握手直接失败。这就是为什么“中间人可以透明转发”在 TLS 里不成立：他能转发，但接不上自己的密钥。

SSH 的做法类似但更直白：交换哈希覆盖双方的版本串、`KEXINIT` 报文和密钥交换材料，主机密钥的签名签在这段哈希上；由此得到的会话标识在同一连接的所有密钥更新中保持不变，重放一次旧握手会被识别。签名与哈希绑在一起，攻击者改了任何一项都要重新签，而没有私钥就签不出来。

应用层也能加一层绑定。把认证令牌与 TLS 通道绑定（比如用通道绑定值参与令牌校验），令牌被复制到另一条连接上就用不了；代价是复杂的代理链会让绑定值失效，所以多数系统只是把它当作可选加强。

还有两个常见误区：

- 把 `http` 改成 `https` 就以为安全了。服务器没配证书、客户端没校验，照样能被中间人截住
- 看到了指纹就点“yes”。指纹的作用是比对，不是仪式；第一次连接时应该从可信渠道核对

第一个误区的技术形态比想象中多：命令行工具的 `-k` 选项、客户端库里关掉校验的开关、容器镜像里缺失的根证书、为了“先跑通”而写进代码的 `verify=False`。这些开关一旦进了生产代码，后面所有的加密都只剩“看起来加密”。第二个误区的问题在于跳过比对就等于放弃认证——指纹每次都要点 yes，说明这个流程没有起到作用。

还有一个现实情况要认：企业网络里常驻着做 TLS 检查的代理，它本身就是“合法中间人”。这类环境里，公钥固定（pinning）会失效，证书链里会出现一张企业自己的根证书。处理办法不是硬顶，而是把固定策略做成可配置的、把企业根证书的安装与审计走正式流程。

## 6.3 越权：比破解更常见

绝大多数数据泄露不是“加密被破解”，而是“权限没写对”。

越权可以分三类。**水平越权**是同角色的用户互相看到对方的数据；**垂直越权**是低权限用户执行了高权限操作；**上下文越权**是跳过了流程约束，比如直接调用“审批通过”的接口，或者把订单从“已完成”改回“待支付”。三类里最常见的是第一类，因为它只需要改一个编号。

最典型的一种叫 IDOR：接口用资源编号直接查询，没有检查归属。

```text
GET /jobs/42
```

这个 42 是谁的任务？如果服务端只按编号查，不判断“这个任务是不是你的”，那么把 42 改成 43，就能看到别人的结果。

修法很朴素：查询条件里永远带上当前用户，`where id = ? and owner_id = ?`。管理接口另开一套，不要用同一个查询加个 `if is_admin` 糊过去。表 6-2 把几种修复模式放在一起比较。

表 6-2　IDOR 的四类修复模式

| 模式 | 做法 | 优点 | 局限 |
|---|---|---|---|
| 查询带主体 | 所有查询强制附加 `owner_id` | 简单、可靠 | 依赖每个人都不忘记写 |
| 不可猜测 ID | 用 UUID 或随机串代替自增 | 降低被枚举的概率 | 不是授权，泄露后照样能用 |
| 能力令牌 | 用带签名的引用代替真实 ID，服务端验签后换取资源 | 可撤销、可限时 | 多一层换取，缓存要设计 |
| 集中授权层 | 把“谁能对什么做什么”抽成策略，统一判定 | 一处修改全局生效 | 初期成本高，策略本身可能写错 |

值得强调的是第三种：把真实对象路径藏起来，对外只暴露一个不透明引用。客户端拿到 `dl/6f3a...`，服务端用这个引用查出真实对象并检查权限。这样做有两个好处：内部结构不外泄，链接泄露之后可以通过吊销引用来止血——纯签名 URL 做不到这一点，它只能等过期。

修 IDOR 时容易漏掉几个地方。批量接口按 ID 列表查询时忘了逐条校验归属；导出接口复用了列表查询但绕过了权限过滤；GraphQL 只校验了顶层对象，嵌套字段暴露了别人的数据；缓存键只用资源 ID 而没带主体，A 的响应被发给了 B；错误信息区分了“不存在”和“无权限”，等于告诉攻击者哪些 ID 是真实存在的。这些都不是密码学问题，都是“检查漏了一遍”。

第二常见的是签名 URL 的范围太大：给外部下载时签了“整个桶、任意方法、七天有效”，等于发了一张长期通行证。正确做法是限定到单个对象、单个方法、尽量短的有效期。收紧可以分四个维度做：方法是 `GET` 还是也允许 `PUT`；对象是单个键、某个前缀，还是整桶；有效期是几分钟还是几天；附加条件是 `Content-Type`、大小上限、来源网段。四个维度里任何一个放到最宽，其余三个的努力都会被削弱。

还有一个结构性建议：把授权检查放在离数据最近的那一层。接口数量会持续增长，列表、导出、批量、嵌套查询，每多一条路径就多一次“忘记检查”的机会；而数据访问路径少得多，在这一层强制加主体条件，漏的概率小一个量级。代价是查询会变唠叨，所以通常写成框架级约束（所有查询必预编译模板），而不是靠代码评审盯人。

## 6.4 SSRF 与端口转发的双刃

端口转发本身是中性的，但它能把“外面够不到的内网”变成“本地能访问的端口”。如果服务端提供了“帮我访问某个地址”的功能，而没做限制，攻击者就能借它去访问内网：

```text
POST /fetch
{"url": "http://169.254.169.254/latest/meta-data/"}
```

这是典型的 SSRF（服务端请求伪造）。云环境里的元数据地址往往能拿到临时凭据，一旦被读到，整台机器的权限就出去了。

这类功能比想象中多。图片抓取与转存、webhook 回调测试、链接预览、PDF 或 HTML 渲染、导入远程仓库、拉取 SSO 元数据、在线 ping 与端口检测，只要“服务端替用户去访问一个 URL”，就是同一个攻击面。攻击者的目标也不止元数据：内网的管理接口、只监听回环的 Redis 与 Elasticsearch、Kubernetes 的 API Server、以及云厂商的内部服务，都在这条路上。

```text
  attacker
     |  POST /fetch  {"url": "http://..."}
     v
  [ app ]  --- no validation --->  egress
                                     |--> 169.254.169.254  (metadata, creds)
                                     |--> 127.0.0.1:6379   (redis, no auth)
                                     |--> 10.0.0.0/8       (internal api)
                                     |--> kubernetes.default.svc
```

绕过校验的手法有一长串，而且都在真实攻防里出现过。IP 可以写成十进制整数、八进制、十六进制，也可以是 `[::ffff:127.0.0.1]` 这样的 IPv6 映射地址；域名可以解析到内网地址，先解析成公网 IP 通过校验，再在请求时改成内网（DNS 重绑定）；`http://expected.com@evil.com/` 这类写法让不同解析器得出不同主机；短链接与 302 跳转可以把“第一次访问”和“最终访问”分开；末尾加个点、改大小写、用 IDN 同形字，都能让字符串匹配失效。

防护思路：

- 只允许访问白名单里的域名或网段
- 解析后的 IP 也要检查，防止 DNS 重绑定
- 禁止访问回环、链路本地、内网网段
- 出站流量走统一的代理，便于审计

四条之外还有一条常被忽略：**校验与连接必须用同一个 IP**。域名通过校验之后，如果在真正建立连接时又解析一次，中间就有被换掉的机会。正确做法是解析一次、把 IP 锁住、在校验过的 IP 上建立连接（并在 HTTP 客户端里把 `Host` 头保留为原域名）。重定向也要逐跳校验，或者干脆禁止重定向，让客户端自己拿着新地址再请求一次。

出站控制是最后一道闸。把“代访问”的服务放进单独的子网，只允许它访问白名单里的目标，禁止它访问元数据地址与内网网段；云上还可以要求元数据服务使用需要令牌的第二种模式（IMDSv2），让“读一个 URL 就拿到凭据”不再成立。这些都属于网络层的手段，比在应用里写正则可靠得多。

堡垒机禁用了端口转发，也是同一个道理：转发会绕过审计，把一条受控的入口变成任意通道。一次 `ssh -L` 就能把数据库端口搬到攻击者本地，而这期间登录日志里只有一条“某人登录了跳板机”，看不出他在访问什么。

## 6.5 最小权限：从密钥管起

一条链路的强度，等于它最弱的一环。常见的弱环不是算法，而是权限：

- 一个密钥能读写整个桶，而它只用来上传日志
- 一个服务用 root 跑，而它只需要读一个目录
- CI 里的令牌能推代码，也能改生产配置
- 离职员工的公钥还在三台机器的 `authorized_keys` 里

最小权限可以拆成四个维度来收紧，见表 6-3。四个维度是乘法关系：只缩短有效期，但范围仍是整库读写，泄露一次照样致命。

表 6-3　最小权限的四个维度

| 维度 | 收紧手段 | 例子 |
|---|---|---|
| 时间 | 短期凭证、自动过期、定期轮换 | 用临时凭据代替长期 AK，有效期按任务时长给 |
| 范围 | 资源粒度收窄到前缀、单对象、单表 | 上传日志的密钥只能写 `logs/2026/` |
| 动作 | 只给必要动词，读写分离 | 报表服务只有只读权限，不含删除 |
| 主体 | 一个用途一个身份，不复用 | 每个服务、每个环境各自一份身份 |

实践里有几条经验值得记。第一，能用角色就不发长期密钥：工作负载从平台拿到短期凭据，凭据到期自动失效，泄露窗口以小时计。第二，给身份起名字，而不是给机器起名字——“订单服务的只读角色”比“10.2.3.4 上的那个密钥”更容易审计。第三，用“最后一次使用时间”做清理，三个月没被调用过的密钥和角色，多半是历史遗留，删掉比留着安全。第四，别让一个身份横跨环境，预发与生产的凭据混用，等于把预发的漏洞直接接到生产上。

最小权限的做法：每个用途一个身份、一份权限，能限定到对象就限定到对象，能短期就短期，能只读就只读。

还有一类权限容易被忘记：**依赖继承的权限**。你的服务以什么身份运行，它引入的第三方代码就以同样的身份运行。所以依赖清单在某种意义上也是权限清单，供应链攻击的全部意义就在于“用你的身份干他的事”。

供应链的风险有几条主线。依赖混淆——内部包名在公共仓库上被抢注一个更高的版本号，构建时优先拉到攻击者的包；名字抢注——把常用包名改一两个字母；维护者账号被接管——一个广受欢迎的包换了主人，新版本里带上一段“安装时执行”的脚本；构建环境被污染——CI 缓存或构建机上的凭据被读走。它们共同的入口都是“自动执行、无人复核”。

对策不复杂，但要落到流程里：锁文件与校验和必须进版本库，构建时用锁定版本而不是浮动范围；内部包走私有源并给它单独的命名空间，公共源里不可能出现同名；安装脚本默认禁用，确实需要时显式白名单；构建产物可复现，能从源码与锁定版本重建出同一个二进制；出站流量受限，即使某段代码被注入也连不上外部地址。这些措施单看都不新鲜，组合起来才能把“一次疏忽”限制成“一次构建失败”。

## 6.6 审计：出事之后能回答三个问题

审计不是“多记日志”，而是出事时能回答：

- 谁做的：是哪个账号、哪个密钥、从哪个地址来
- 做了什么：执行了哪些命令、读写哪些对象
- 什么时候：时间线能不能对上

三问之外还有两个隐含要求。一是**可串联**：同一个用户请求在网关、应用、数据库里留下三条记录，必须有一个共同的请求编号把它们连起来，否则时间线只能靠猜。二是**可信任**：日志能被攻击者改写，审计就失去意义，所以关键日志要写到攻击者改不到的地方——单独账号的存储、只追加的桶、或者外部集中采集。

要做到这三点，日志里必须带身份和请求编号，且能串起来。会话录像、命令记录、对象访问日志，属于不同层，缺一层就会有一段空白。

一条有用的审计记录通常包含这些字段：时间戳（UTC，带时区）、主体（账号、角色、凭据指纹）、动作（读写删、读的是哪个对象）、结果（成功、拒绝、报错）、来源（IP、用户代理）、关联 ID（trace id 或请求 id）、以及策略判定（命中了哪条规则）。表 6-4 把三问对应的字段与常见缺口列在一起。

表 6-4　审计三问与字段缺口

| 问题 | 关键字段 | 常见缺口 |
|---|---|---|
| 谁做的 | 账号、角色、凭据指纹 | 共用账号、只记 IP 不记身份 |
| 做了什么 | 动作、资源标识、结果 | 只记“访问了接口”，不记对象 |
| 什么时候 | UTC 时间戳、耗时 | 本地时间、时钟不同步 |
| 怎么串起来 | 请求 ID、trace ID | 网关与应用的 ID 不互通 |

审计日志还有成本与隐私两侧。成本上，全量记录对象级访问在流量大的系统里是天文数字，通常的做法是控制面全记、数据面采样并保留聚合统计；隐私上，日志里不能出现密钥、令牌、密码原文，需要标识时记指纹或前缀。保留期则要和合规要求对齐：短了查不了历史，长了是负债，因为备份里的旧日志同样会泄露。

审计与告警要分开看。审计为“事后回答”服务，要求完整、可查、不可改；告警为“事中发现”服务，只能建在抽样与模式上，否则每天都会被噪声淹没。可用的告警规则通常很朴素：同一凭据在短时间内从相隔很远的地点登录、某个身份突然大量读敏感对象、一分钟内大量权限拒绝、管理接口在非工作时间被调用。这些规则背后的逻辑是一致的——异常不是“看起来奇怪”，而是与这个身份的基线不同，所以先有基线，再谈告警。

## 6.7 这一章记住什么

- 先写威胁模型，再谈加固；没有目标的“安全”只是配置堆砌。
- 加密、认证、绑定三层缺一不可；`https` 三个字不等于安全。
- 越权比破解常见：查询永远带归属条件。
- 端口转发与“代访问”功能是 SSRF 的入口，要做白名单与出站控制。
- 最小权限与可追溯的审计，是长期有效的两件事。
- 依赖以你的身份运行：锁定版本、隔离源、限制出站，等于给供应链上锁。
