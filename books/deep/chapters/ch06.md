# 安全边界：中间人、越权与最小权限

## 6.1 先把威胁模型写下来

“安全”不是一个可以打勾的状态。谈安全之前，先回答三个问题：

- 我要保护什么：登录凭证、用户数据、计算结果、服务器本身
- 谁会来攻击：路过的扫描器、同网段的邻居、被钓鱼的员工、拿到一枚密钥的外部人
- 攻击者能站在哪里：公网、内网、服务器上、供应链里

这三个问题决定了该防什么。没有威胁模型的“加固”，往往只是加了几个配置项，真正的入口还开着。

## 6.2 中间人：三种防线

中间人的位置很尴尬也很强大：他在你和服务器之间，可以转发、可以改、可以伪造。

防线有三层：

- **加密**：让内容不可读。这挡不住篡改，但让窃听失去意义
- **认证**：确认对面是谁。SSH 用主机密钥与指纹，HTTPS 用证书
- **绑定**：把“这次连接”和“这次认证”绑在一起，比如签名里带上会话标识与交换哈希

三层缺一层都有问题：只加密不认证，中间人可以冒充服务器；只认证不绑定，攻击者可以把一次握手的材料搬到另一次连接里重用。

还有两个常见误区：

- 把 `http` 改成 `https` 就以为安全了。服务器没配证书、客户端没校验，照样能被中间人截住
- 看到了指纹就点“yes”。指纹的作用是比对，不是仪式；第一次连接时应该从可信渠道核对

## 6.3 越权：比破解更常见

绝大多数数据泄露不是“加密被破解”，而是“权限没写对”。

最典型的一种叫 IDOR：接口用资源编号直接查询，没有检查归属。

```text
GET /jobs/42        # 42 是谁的任务？
```

如果服务端只按编号查，不判断“这个任务是不是你的”，那么把 42 改成 43，就能看到别人的结果。

修法很朴素：查询条件里永远带上当前用户，`where id = ? and owner_id = ?`。管理接口另开一套，不要用同一个查询加个 `if is_admin` 糊过去。

第二常见的是签名 URL 的范围太大：给外部下载时签了“整个桶、任意方法、七天有效”，等于发了一张长期通行证。正确做法是限定到单个对象、单个方法、尽量短的有效期。

## 6.4 SSRF 与端口转发的双刃

端口转发本身是中性的，但它能把“外面够不到的内网”变成“本地能访问的端口”。如果服务端提供了“帮我访问某个地址”的功能，而没做限制，攻击者就能借它去访问内网：

```text
POST /fetch
{"url": "http://169.254.169.254/latest/meta-data/"}
```

这是典型的 SSRF（服务端请求伪造）。云环境里的元数据地址往往能拿到临时凭据，一旦被读到，整台机器的权限就出去了。

防护思路：

- 只允许访问白名单里的域名或网段
- 解析后的 IP 也要检查，防止 DNS 重绑定
- 禁止访问回环、链路本地、内网网段
- 出站流量走统一的代理，便于审计

堡垒机禁用了端口转发，也是同一个道理：转发会绕过审计，把一条受控的入口变成任意通道。

## 6.5 最小权限：从密钥管起

一条链路的强度，等于它最弱的一环。常见的弱环不是算法，而是权限：

- 一个密钥能读写整个桶，而它只用来上传日志
- 一个服务用 root 跑，而它只需要读一个目录
- CI 里的令牌能推代码，也能改生产配置
- 离职员工的公钥还在三台机器的 `authorized_keys` 里

最小权限的做法：每个用途一个身份、一份权限，能限定到对象就限定到对象，能短期就短期，能只读就只读。

## 6.6 审计：出事之后能回答三个问题

审计不是“多记日志”，而是出事时能回答：

- 谁做的：是哪个账号、哪个密钥、从哪个地址来
- 做了什么：执行了哪些命令、读写哪些对象
- 什么时候：时间线能不能对上

要做到这三点，日志里必须带身份和请求编号，且能串起来。会话录像、命令记录、对象访问日志，属于不同层，缺一层就会有一段空白。

## 6.7 这一章记住什么

- 先写威胁模型，再谈加固；没有目标的“安全”只是配置堆砌。
- 加密、认证、绑定三层缺一不可；`https` 三个字不等于安全。
- 越权比破解常见：查询永远带归属条件。
- 端口转发与“代访问”功能是 SSRF 的入口，要做白名单与出站控制。
- 最小权限与可追溯的审计，是长期有效的两件事。
