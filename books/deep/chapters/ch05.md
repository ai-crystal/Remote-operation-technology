# 性能与并发：加密开销、连接复用与背压

## 5.1 加密的真实成本

对称加密的吞吐在现代 CPU 上很高：带 AES-NI 的机器，AES-GCM 能跑到几 GB/s，ChaCha20-Poly1305 在手机上更有优势（没有 AES 硬件加速时）。

所以“加密慢”在今天基本是个过时的印象。真正影响性能的通常是下面几件事：

- 每条连接都要做一次非对称运算（密钥交换与签名），这部分比对称加密慢几个数量级
- 每条连接都要分配缓冲、维护状态
- 大量短连接会让握手成本占比飙升
- 反向代理、日志、序列化，往往比加密更贵

结论：优化方向不是“换更快的加密算法”，而是“减少握手次数、减少数据拷贝、减少同步点”。

## 5.2 连接复用：一条连接能装多少东西

SSH 的连接层支持多路复用：一条加密连接里可以同时开多个通道，交互式 shell、文件传输、端口转发各占一路。

每条连接能开多少通道，受服务端 `MaxSessions` 限制，默认是 10。VS Code 的远程开发会同时用掉好几路：文件服务、终端、扩展通信各一路，所以在 10 的上限下偶尔会碰到 `open failed: administratively prohibited`——这不是网络问题，是通道用完了。

复用的收益很直接：一次握手，多次使用。代价是所有通道共享同一条 TCP 连接，一旦这条连接的网络质量变差，所有通道一起受影响；一个通道把带宽吃满，其他通道也会被拖慢。

## 5.3 服务端的并发模型

同样的接口，用不同的并发模型写，表现差别很大。

- **每连接一个进程**：隔离好，代价是内存与上下文切换
- **每连接一个线程**：比进程轻，但线程一多，调度和锁的争用就上来了
- **事件循环（异步）**：单线程处理大量连接，适合 I/O 密集；一旦有阻塞操作（比如同步读磁盘、调用外部接口），整个循环被卡住

判断自己的服务属于哪一类，看它最耗时的部分是什么。CPU 密集（比如图像处理）就别指望单个事件循环解决，要把任务丢进 worker 队列；I/O 密集（比如转发、查询）用异步更划算。

## 5.4 队列与背压

长任务一定要有队列，但队列必须有界。

无界队列在压力下会做一件很糟的事：把内存吃光，然后整个进程被杀。有界队列则会明确地拒绝：队列满了返回 `429`，让调用方等一会儿再来。

这就是背压：上游生产得太快，下游消化不了，系统要能把这个信号传回去，而不是默默堆积。

实践中三件事一起做：

- 队列容量有上限，满了就拒绝，并告诉对方多久后重试
- 每个任务有超时，卡住的任务要能被清理
- 有监控：队列长度、等待时间、失败率，任一异常就告警

判断“队列是不是太长”，可以用一个粗略的估算：队列长度 ÷ 每秒处理数 = 平均等待秒数。等待时间超过用户能接受的上限，就该扩容或限流了。

## 5.5 限流的三种常见算法

- **计数器**：单位时间内的请求数超过阈值就拒绝。实现最简单，边界处会有突刺
- **滑动窗口**：把时间切成小格，统计最近一段窗口的请求数，边界更平滑
- **令牌桶**：桶里以固定速率放令牌，每个请求取一个；桶有容量上限，允许短时突发

令牌桶最适合“平时平稳、偶尔突发”的场景，也是大多数网关默认的做法。返回 `429` 时带上 `Retry-After`，客户端才知道该等多久。

## 5.6 看什么指标

不要只看平均延迟。平均 50 毫秒可能意味着“大多数人很快，少数人卡了十秒”。

至少看四个数：

- **P50**：一半请求在这个时间内完成
- **P95 / P99**：长尾有多长，用户抱怨的通常是这一部分
- **错误率**：按状态码分类，4xx 和 5xx 要分开看
- **排队时间**：任务从入队到开始执行的间隔

长尾往往由少数几个原因造成：某个查询没走索引、某个外部接口偶发超时、GC 停顿、锁竞争。把 P99 的请求抽样出来看，比盯着平均值有用得多。

## 5.7 这一章记住什么

- 加密不是瓶颈，握手、拷贝和同步点才是。
- 连接复用能省握手，但所有通道共享同一条连接的质量。
- 队列必须有界，满了要拒绝；拒绝要告诉对方多久后重试。
- 看 P95/P99 和排队时间，不要只看平均延迟。
