# 性能与并发：加密开销、连接复用与背压

## 5.1 加密的真实成本

对称加密的吞吐在现代 CPU 上很高：带 AES-NI 的机器，AES-GCM 能跑到几 GB/s，ChaCha20-Poly1305 在手机上更有优势（没有 AES 硬件加速时）。

把“几 GB/s”换成更具体的量级：单核 AES-128-GCM 通常 3–7 GB/s，AES-256-GCM 因为轮数更多，通常低 20%–40%；ChaCha20-Poly1305 在有 AVX2 的 x86 上通常 1–3 GB/s，在带加密扩展的 ARM 上也接近 GB/s 级，在无加速的老式 ARM 上会掉到几百 MB/s。折算成每字节成本，5 GB/s 相当于 0.2 纳秒，加密 1 KiB 大约 0.2 微秒。

真正贵的是非对称运算。一次 X25519 密钥交换通常几十微秒，一次 ECDSA P-256 签名几十到两百微秒，一次 RSA-2048 私钥运算几百微秒到两毫秒。表 5-1 把它们换算成“等价于加密多少数据”，用同一个尺度看差距。

表 5-1　非对称运算与对称加密的量级对比（现代 x86 单核，随实现与 CPU 波动很大）

| 运算 | 典型单次耗时 | 等价于 AES-GCM 加密的数据 |
|---|---|---|
| AES-128-GCM，1 KiB | 约 0.2 μs | 1 KiB |
| X25519 密钥交换 | 30–80 μs | 150–400 KiB |
| ECDSA P-256 签名 | 50–200 μs | 250 KiB–1 MiB |
| RSA-2048 私钥运算 | 0.5–2 ms | 2.5–10 MiB |
| 证书链验证（2–3 张） | 0.5–2 ms | 2.5–10 MiB |

这张表解释了一件事：一条连接的握手成本，大约等于加密几十 KB 到几 MB 数据。所以“加密慢”在今天基本是个过时的印象。真正影响性能的通常是下面几件事：

- 每条连接都要做一次非对称运算（密钥交换与签名），这部分比对称加密慢几个数量级
- 每条连接都要分配缓冲、维护状态
- 大量短连接会让握手成本占比飙升
- 反向代理、日志、序列化，往往比加密更贵

数据拷贝值得单独看一眼。典型路径是：应用写进用户态缓冲，加密后拷进内核 socket 缓冲，网卡 DMA 读走。两条 10 Gbps 的连接跑满时，这些拷贝是实打实的 CPU 与内存带宽开销，所以内核 TLS、`sendfile`、零拷贝这类手段才会被反复提起。另一项隐性成本是记录切分：TLS 1.3 的单条记录上限通常是 16 KiB，每条记录单独加密并附 16 字节认证标签，切得太碎会让每字节的固定开销占比上升。

结论：优化方向不是“换更快的加密算法”，而是“减少握手次数、减少数据拷贝、减少同步点”。

## 5.2 连接复用：一条连接能装多少东西

握手贵在哪，先算一笔账。以 TLS 1.3 为例，首次握手是 1 个 RTT，加上 TCP 三次握手的 1 个 RTT，新建一条连接至少等 2 个 RTT；TLS 1.2 是 2 个 RTT，加上 TCP 就是 3 个。RTT 50 毫秒时，这意味着 100–150 毫秒的纯等待，期间没有任何业务数据在传。

握手还有 CPU 的那一半：一次 X25519、一次证书链验证、若干次记录层运算。两者相乘就是每秒新建连接的成本。假设每次握手消耗 100 微秒 CPU，每秒建立一万条连接，就需要一秒 CPU/秒，也就是一个核满载，而业务逻辑还没开始跑。所以“短连接 + 高并发”是性能问题最常见的来源，不是加密算法。

证书链的大小也在账上。链上多一张中间证书，就多几百字节到几 KB 的传输和一次签名验证；OCSP 装订（stapling）能把“再去问一次吊销状态”的往返省掉，代价是服务端要定期刷新装订内容，装订过期反而会让客户端拒绝连接。

SSH 的连接层支持多路复用：一条加密连接里可以同时开多个通道，交互式 shell、文件传输、端口转发各占一路。

每条连接能开多少通道，受服务端 `MaxSessions` 限制，默认是 10。VS Code 的远程开发会同时用掉好几路：文件服务、终端、扩展通信各一路，所以在 10 的上限下偶尔会碰到 `open failed: administratively prohibited`——这不是网络问题，是通道用完了。

并发新建连接还受 `MaxStartups` 限制，OpenSSH 的默认值通常写作 `10:30:100`：未认证连接到 10 条开始按概率丢弃，到 30 条丢 30%，到 100 条全部拒绝。这两个参数一起解释了为什么“能连上但开不了新终端”和“连都连不上”是两种不同的故障，排查时先分清是哪一层被挡。

HTTP 侧的限制长得不一样，但道理相同，见表 5-2。

表 5-2　几种传输层的复用单位与上限

| 协议 | 复用单位 | 并发上限 | 主要瓶颈 |
|---|---|---|---|
| HTTP/1.1 | 一条连接一个请求 | 浏览器惯例每域名 6 条 | 连接数与握手 |
| HTTP/2 | stream | `SETTINGS_MAX_CONCURRENT_STREAMS`，常见 100 以上 | 单 TCP 的连接级队头阻塞 |
| HTTP/3 | stream | 同上 | 基本没有队头阻塞，受拥塞控制约束 |
| SSH | channel | `MaxSessions`，默认 10 | 单连接带宽 |

复用的收益很直接：一次握手，多次使用。代价是所有通道共享同一条 TCP 连接，一旦这条连接的网络质量变差，所有通道一起受影响；一个通道把带宽吃满，其他通道也会被拖慢。HTTP/2 的队头阻塞就属于这一类：丢一个包，整条连接上所有 stream 的交付都往后排，即使它们分属不同请求。

连接池还有一类不显眼但很常见的故障：空闲超时竞态。服务端或中间的负载均衡器通常有 60 秒左右的空闲超时，客户端池子里留着的连接看起来还能用，实际已经被对端关闭；客户端在超时边缘复用它，得到的是 `RST` 或 502。解决办法是让客户端的最长空闲时间明显短于服务端（比如 30 秒对 60 秒），并对“连接已断”这类错误做一次幂等重试，而不是把连接池调大。

## 5.3 服务端的并发模型

同样的接口，用不同的并发模型写，表现差别很大。

- **每连接一个进程**：隔离好，代价是内存与上下文切换
- **每连接一个线程**：比进程轻，但线程一多，调度和锁的争用就上来了
- **事件循环（异步）**：单线程处理大量连接，适合 I/O 密集；一旦有阻塞操作（比如同步读磁盘、调用外部接口），整个循环被卡住

还有第四种：**协程**。Go 的 goroutine、Rust 的 async 任务、Java 的虚拟线程都属于这一类，本质是“用户态调度 + 少量内核线程”，把“每连接一个执行流”的写法保留下来，同时把每个执行流的内存成本压到 KB 级。表 5-3 把四者的量级摆在一起。

表 5-3　四种并发模型的量级对比

| 模型 | 单连接内存 | 切换成本 | 常见并发上限 | 主要风险 |
|---|---|---|---|---|
| 每连接一进程 | MB 级 | 高（内核调度、地址空间切换） | 数百 | 内存与 fork 成本 |
| 每连接一线程 | 栈默认 8 MB 虚拟、驻留几十 KB | 中（内核调度） | 数千 | 锁争用、栈耗尽 |
| 事件循环 | 每连接一个 fd 加读写缓冲 | 极低（函数调用） | 数万到数十万 | 一次阻塞拖垮全部 |
| 协程 | 初始 2–8 KB 栈，按需增长 | 低（用户态） | 数万到百万 | 阻塞调用占满线程池 |

判断自己的服务属于哪一类，看它最耗时的部分是什么。CPU 密集（比如图像处理）就别指望单个事件循环解决，要把任务丢进 worker 队列；I/O 密集（比如转发、查询）用异步更划算。

事件循环的软肋是“看起来异步、其实阻塞”的调用。同步 DNS 解析、同步文件读写、同步日志落盘、拿不到就等的锁，任何一项都会把整个循环按住；症状是所有连接一起变慢，而不是某一个请求慢。协程模型的软肋类似，只是表现形式是线程池被占满、新任务排队，而不是循环停转。

现实中的服务多半是混合模型。nginx 是一个 master 加若干 worker，每个 worker 跑一个事件循环，CPU 密集的活儿交给上游；Go 服务用 `GOMAXPROCS` 限制参与调度的核数，把重计算丢进带缓冲的 worker 池；Java 用虚拟线程处理请求，用固定线程池兜住数据库连接。这些做法的共同点是：**慢的部分隔离出去，快的部分保持非阻塞**。

## 5.4 队列与背压

长任务一定要有队列，但队列必须有界。

无界队列在压力下会做一件很糟的事：把内存吃光，然后整个进程被杀。有界队列则会明确地拒绝：队列满了返回 `429`，让调用方等一会儿再来。

这就是背压：上游生产得太快，下游消化不了，系统要能把这个信号传回去，而不是默默堆积。

判断“队列是不是太长”，可以用一个粗略的估算：队列长度 ÷ 每秒处理数 = 平均等待秒数。这个式子其实就是排队论里的利特尔法则（Little's law）：系统内的平均任务数 `L`、到达速率 `λ`、平均停留时间 `W` 满足 `L = λW`。反过来用就是容量设计——每秒处理 200 个任务、希望最多等 5 秒，队列容量大约 1000；超过这个数就该拒绝，而不是继续往内存里塞。

等待时间随利用率上升得快得惊人。在单队列单服务的近似模型里（M/M/1），平均停留时间是服务时间除以“剩余能力”：`W = S / (1 - ρ)`，其中 `S` 是平均服务时间，`ρ = λS` 是利用率。ρ 为 50% 时平均等一倍服务时间，80% 时 5 倍，90% 时 10 倍，95% 时 20 倍。这条曲线解释了为什么“CPU 才用了七成”也可能开始排队，以及为什么把利用率推到 90% 以上换吞吐很不划算。

队列满了之后的处理方式有四种，见表 5-4；选哪种，决定了系统失败时的样子。

表 5-4　队列满时的四种策略

| 策略 | 满时行为 | 优点 | 代价 |
|---|---|---|---|
| 无界 | 继续接收 | 不丢任务 | 内存耗尽后被 OOM 杀掉 |
| 有界 + 拒绝 | 立刻返回 429 | 行为可预测，保护下游 | 调用方必须会重试 |
| 有界 + 丢最旧 | 挤掉排队最久的 | 新任务延迟稳定 | 任务丢失，需要幂等 |
| 有界 + 阻塞生产者 | 反压回上游 | 不丢任务 | 上游线程被拖住，可能连锁阻塞 |

实践中三件事一起做：

- 队列容量有上限，满了就拒绝，并告诉对方多久后重试
- 每个任务有超时，卡住的任务要能被清理
- 有监控：队列长度、等待时间、失败率，任一异常就告警

还有一件常被忽略的事：**超时要有预算**。一次请求进来，总预算是 2 秒，那么每个下游调用分到的额度要依次递减（1.5 秒、1 秒、0.5 秒），而不是每层都写“超时 30 秒”。没有预算的超时会层层叠加，用户早在第 3 秒就走了，服务还在替他的请求占着线程和连接。

背压也不总要靠自己实现。TCP 有接收窗口，下游读得慢，窗口变小，上游的发送就会被阻塞；HTTP/2 有 `WINDOW_UPDATE` 帧，流控粒度到单个 stream；消息队列有 prefetch 或 QoS 上限，在途消息到顶就不再推送。这些机制的共同点是：把“我处理不过来”变成发送方能感知的信号，而不是让缓冲无声地膨胀。

## 5.5 限流的三种常见算法

- **计数器**：单位时间内的请求数超过阈值就拒绝。实现最简单，边界处会有突刺
- **滑动窗口**：把时间切成小格，统计最近一段窗口的请求数，边界更平滑
- **令牌桶**：桶里以固定速率放令牌，每个请求取一个；桶有容量上限，允许短时突发

固定窗口的突刺值得算一下。限额是每分钟 100 次，如果客户端在 12:00:59 发 100 次、在 12:01:01 再发 100 次，那么两秒内通过了 200 次，是限额的两倍。这不是客户端作弊，而是窗口边界处的必然现象；请求量越大，这个瞬时倍率越接近 2。

滑动窗口有两种实现。“日志法”把每次请求的时间戳记下来，统计最近 60 秒内的条数，精确但内存与请求数成正比；“计数法”只保留上一格的计数，按重叠比例加权：

```text
window = 60s
estimated = prev_count * (1 - elapsed_in_current / window) + curr_count
allow if estimated < limit
```

它只用两个整数，误差有界，绝大多数网关用的是这个变体。

令牌桶最适合“平时平稳、偶尔突发”的场景，也是大多数网关默认的做法。它的参数只有两个：速率 `r`（每秒放多少令牌）和容量 `b`（桶能存多少）。长期平均被限制在 `r`，瞬时可以花掉攒下来的 `b`，所以批处理、页面首屏这类“一阵一阵”的流量不会被误伤。

```text
on_request(now):
    tokens = min(capacity, tokens + (now - last_refill) * rate)
    last_refill = now
    if tokens >= 1:
        tokens -= 1
        allow
    else:
        reject with Retry-After = ceil((1 - tokens) / rate)
```

漏桶是它的对偶：请求先进一个有界队列，出口以恒定速率放行，队列满了就丢。它不许突发，换来的是输出极其平滑，适合保护脆弱的下游（老式存储、第三方接口）。表 5-5 把几种算法放在一起比较。

表 5-5　限流算法的对比

| 算法 | 允许突发 | 状态开销 | 边界精度 | 典型用途 |
|---|---|---|---|---|
| 固定窗口计数器 | 边界处可到 2 倍 | 一个计数 | 差 | 粗粒度配额、日志采样 |
| 滑动窗口计数 | 少量 | 两个计数 | 较好 | 网关默认限流 |
| 滑动窗口日志 | 无 | 与请求数成正比 | 精确 | 低流量、强合规场景 |
| 令牌桶 | 有，上限为桶容量 | 两个数（令牌数、时间） | 好 | API 配额、允许突发的场景 |
| 漏桶 | 无 | 队列长度 | 好 | 保护脆弱下游 |

单机限流好办，分布式限流难在“共享状态”。常见做法有三种：把计数放在中心存储里用原子脚本更新，精度高但每次请求多一次往返；给每台机器分配 `r / N` 的配额，没有中心依赖但集群规模变化时要重算，且实际总速率会在 `r` 附近抖动；按请求的某个键（用户、租户、IP）做一致性哈希，把同一个键的请求固定到同一台机器上计数。三种方案都能用，选哪种取决于你能容忍多少误差、以及中心存储挂掉时要不要放行。

返回 `429` 时带上 `Retry-After`，客户端才知道该等多久。只回一个裸的 429，等于让客户端自己猜，猜错就是重试风暴。限流还要区分“拒绝”和“排队”：能等的工作放进带超时的队列，不能等的（交互式请求）直接拒绝。

## 5.6 看什么指标

不要只看平均延迟。平均 50 毫秒可能意味着“大多数人很快，少数人卡了十秒”。

至少看四个数：

- **P50**：一半请求在这个时间内完成
- **P95 / P99**：长尾有多长，用户抱怨的通常是这一部分
- **错误率**：按状态码分类，4xx 和 5xx 要分开看
- **排队时间**：任务从入队到开始执行的间隔

分位数有两个容易踩的坑。第一，分位数不能求平均：两个实例的 P99 分别是 100 毫秒和 900 毫秒，平均成 500 毫秒没有任何意义，真实合并后的 P99 可能远超 900。正确做法是保留直方图（HDR histogram、t-digest 之类）再做合并，或者按实例分别看。第二，聚合粒度决定精度：按分钟聚合的 P99 会把一分钟内的毛刺抹平，长尾问题要看更细的窗口，或者直接抽样慢请求的调用链。

尾延迟会被放大。一个请求要串行调用 10 个下游，每个下游有 1% 的概率慢，那么这个请求变慢的概率约是 `1 - 0.99^10 ≈ 9.6%`——也就是说，单个组件“99% 都很快”，组合起来就变成“每十个请求有一个慢”。这解释了为什么微服务化之后 P99 突然变差，而每个服务的指标看起来都正常。缓解手段是并行化、设超时与降级、以及对慢副本做请求对冲（hedging）。

长尾往往由少数几个原因造成：某个查询没走索引、某个外部接口偶发超时、GC 停顿、锁竞争。把 P99 的请求抽样出来看，比盯着平均值有用得多。指标之外还要看饱和度：连接池占用、线程池队列、文件描述符、内存水位。常用的两套检查清单是 USE（利用率、饱和度、错误）和 RED（速率、错误、时长），选一套坚持用就行。

**压测怎么做**。压测的目标不是“打出一个漂亮数字”，而是找到拐点：延迟开始非线性上升的那个负载点。做法是阶梯加压——每档稳定跑几分钟，记录吞吐、P50、P99、错误率、CPU 与队列长度，然后画出来。三个常见误区值得提前避开：一是用固定并发数而不是固定到达速率，导致系统变慢时压力反而变小，测不出真实的过载行为；二是忽略数据量与冷缓存，测试库里只有几千行、缓存全命中，数字好看但没有意义；三是只压单机不看全链路，瓶颈往往在数据库连接数、DNS、或者某个共享的限流器上。

## 5.7 这一章记住什么

- 加密不是瓶颈，握手、拷贝和同步点才是。
- 连接复用能省握手，但所有通道共享同一条连接的质量。
- 队列必须有界，满了要拒绝；拒绝要告诉对方多久后重试。
- 看 P95/P99 和排队时间，不要只看平均延迟。
- 利用率超过八成之后，排队时间开始非线性增长；压测要找拐点，不是找最高分。
